## What this is

A Vite + React + TypeScript web app for practicing Chinese-language exam questions (Primary school Chinese / Higher Chinese, Singapore-style "语文应用": cloze, error correction, reading comprehension, dialogue completion, hanyu pinyin, etc.), with a Tamagotchi-style gamification layer (earn BP for correct answers, hatch and grow a pet owl, feed/play with it via a shop + bag). No backend required — works fully offline once built/served. Every visitor lands on a login page first, but can click through as a guest with one tap and never see it again on that device; login is optional, and when unconfigured (no Supabase project), sign-in/sign-up just show a "not configured" error while guest mode still works with zero setup.

## Running / testing

Standard Vite/npm project — no test suite (verify changes by running the dev server and clicking through the flow manually):

- `npm install` — React 19; `@supabase/supabase-js` backs optional login/sync; `yaml` parses the runtime-fetched content files under `public/content/`; `tsx` runs the one-off scripts under `scripts/`.
- Login/sync needs a Supabase project: run `supabase/schema.sql` once in its SQL editor, copy `.env.example` to `.env.local` and fill in `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`, and turn off **"Confirm email"** (Authentication → Providers → Email) — usernames are mapped to a synthetic, unreachable `@example.com` address (see the Auth section), so a confirmation-required project leaves every signup permanently stuck unconfirmed. Both `npm run dev`/`build` work fine with no `.env.local` at all (`src/lib/supabase.ts` exports `null` instead of throwing) — fully local/offline exactly as before.
- `npm run dev` / `npm run build` (`tsc -b && vite build` — always run at least `npx tsc -b` after non-trivial changes, no test suite otherwise) / `npm run lint` (`oxlint`) / `npm run preview`.
- `npm run build-content-index` — regenerates the three `index.yaml` files under `public/content/<level>/` (defaults to `p5`; pass a level id to target another). **Run this after hand-editing any content file** — the index isn't recomputed automatically, so a stale index silently keeps serving pre-edit lesson counts/category availability.

## Architecture

### Content files (`public/content/<level>/`)
Practice content (questions, Tingxie lessons, Read-a-Story passages) lives as human-editable YAML/Markdown under `public/content/<level>/`, fetched at runtime — not bundled, not TS/JSON literals. **Edit files there, not `src/data/*.ts`** — those are thin fetch+cache loaders, not the data itself.

- `meta.yaml` — `label`/`lessonCount` for the level.
- `questions/<category>.yaml` — one file per category (`CATEGORIES` in `data/questions.ts`), each a list of "groups" (a standalone question, or a passage + every question sharing it, always graded together). `data/questions.ts`'s `parseQuestionCategoryYaml()` is the one function that expands the on-disk shape into the runtime `QuestionGroup`/`Question` shape (`data/types.ts`) — shared by the app's loader and `scripts/build-content-index.ts`, so both validate content identically (a `correct` matching no option throws immediately in either). Two on-disk shapes:
  - **Flat categories** (`pinyin`/`vocab`/`phrase`/`usage`/`conjunction`/`sentence`): always one MCQ question, `subject: Chinese` — authored as just `questionID`/`lessonIds`/`question`/`options`/`correct`. `correct` matches an option's **text**, not a position/key, so reordering options by hand can't silently desync the answer.
  - **Passage categories** (`cloze`/`comprehension`/`dialogue`/`errorcorrect`/`practical`): keep `groupId`/`passage`/`questions[]`; per-category-constant fields (`subject`, `format`, `marks`) default in via `CATEGORY_DEFAULT_SUBJECT`/`CATEGORY_DEFAULT_FORMAT` in `data/questions.ts` instead of being authored, except where a category genuinely mixes values (`cloze`/`comprehension` mix Chinese/Higher Chinese, so `subject` stays required there).
  - `lessonIds` on `pinyin`/`vocab`/`phrase`/`usage` was matched against each lesson's real taught-vocab list (see git history for the method if redoing this for new content) — `conjunction`/`sentence`'s `lessonIds` is just "whichever exam paper this came from," **not** vocab-verified, so don't treat it as reliable for lesson-filtering accuracy.
- `tingxie/<n>.yaml` — one file per lesson; each `vocab[]` entry carries its own optional `sentenceBank` (Apply's example sentences).
- `stories/<n>.md` — one Markdown file per written lesson (`# Title`, `## Page N` sections, blank-line-separated paragraphs, **one hand-split sentence per line** — Chinese dialogue punctuation doesn't split cleanly with a generic regex, so this is authored by hand, not computed at runtime). A lesson with no file gets a client-side placeholder (`data/stories.ts`'s `placeholderLesson()`) instead of a 404.
- `scripts/migrate-content.ts`/`migrate-question-schema.ts` are one-off migrations, kept for reference only — don't re-run against already-migrated content. `scripts/build-content-index.ts` is the one you run regularly (see above).
- **Levels**: `p5` (full real content) and `p2` (real content for `cloze`/`comprehension`/`pinyin`/`vocab`/`usage` only — its other categories are dummy placeholders, gated out of the UI via `LevelInfo.relevantCategories`/`isCategoryRelevantForLevel()` in both `Practice.tsx`'s picker and `lib/typeSession.ts`'s `selectTypeSessionGroups()` as defense-in-depth). Add a level: new `public/content/<level>/` dir, same shape, one line in `data/levels.ts`'s `LEVELS`.
  - `data/levels.ts` holds a plain module-level `currentLevel` (read by the data loaders, which are plain async functions, not components) **alongside** `AppState.level` (the React-visible copy) — kept in sync only by convention: every level-changing call site must call `setCurrentLevel()` **and** dispatch `SET_LEVEL` together (currently only `LevelBar.tsx`). Switching resets `AppState` to `{ ...initialState, level }` and is persisted + synced cross-device (`state/levelPreference.ts`, see Auth/sync below).
  - Every module-level content cache is keyed by level, so a level switch can't serve the wrong level's cached data.
- **Prefetching**: each data loader has a fire-and-forget `prefetchAll*`/`prefetch*Lessons` warmup (called once its index loads) so a real click on the hosted (Vercel) deployment usually resolves from cache instead of a live round trip. `vercel.json` also cache-headers `/content/*`.

### Data layer (`src/data/`)
Thin fetch+cache loaders, plus a few plain-constant config modules:
- `types.ts` — shared interfaces (`Question`, `QuestionGroup`, `PetState`, `Achievement`, Tingxie/Story content shapes, ...).
- `questions.ts` / `tingxie.ts` / `stories.ts` — fetch+cache the respective content type (module-level `Map` caches, keyed by level). `questions.ts` also holds stable app config (`CATEGORIES`, `VOCABULARY_CATEGORY_KEYS`, `SUBJECTS`) and `computeCategorySubjects()`.
- `pet.ts` — pet/BP tunable config (stage thresholds, BP rates, shop items, toy minigame configs, Special Quest types) — **not** per-user state. Age (`getAge(growth)`, `state/PetContext.tsx`) is purely derived (`growth / GROWTH_PER_AGE_YEAR`, 100 growth = 1 "year"); the growth bar deliberately only shows progress within the current age year, never how far off the next stage is.
- `levels.ts` — the level registry, see above.

### App state layer (`src/state/AppStateContext.tsx`)
`useReducer` + two Contexts. Holds `screen`, the active quiz session, picker selections, and the question-bank bootstrap (`questionIndex`/`categorySubjects`/`lessonCount`/`questionIndexLoaded`, populated by `App.tsx`'s `ScreenRouter` fetching `meta.yaml`+`questions/index.yaml` once on mount). **This has to live in `AppState`, not a separate Context**: `SELECT_SUBJECT` reads `categorySubjects` synchronously inside the reducer, and a reducer can't await a fetch or read Context. `RESET_TO_HOME` preserves the bootstrap fields (and `selectedSubject`/`selectedCategories`/`selectedLessons`/`level`) so "back to home" never re-triggers the bootstrap fetch or silently reverts a picker choice.

Lesson-filter invariant: `selectedLessons: Set<number>` — **empty means "all lessons"**, not "none". Any action changing `selectedCategories` resets it to empty unless the result still has all of `VOCABULARY_CATEGORY_KEYS` selected (`vocabRetained()`), so a lesson filter left over from a since-deselected Vocabulary can't sit there invisibly.

### Screens (`src/components/`)
Each top-level screen is its own folder; shared UI is in `components/common/` (`Modal.tsx`'s `ConfirmModal`, `OwlArt.tsx`, `TopNav.tsx`, `CompleteScreen.tsx` — a shared "session finished" screen used by Tingxie's Learn/Apply/Test/Play and Read a Story).

- **`TopNav.tsx`**: persistent 5-item nav, hidden on `"quiz"`/`"result"` (which have their own leave-confirmation flow instead).
- **Practice** (`Practice.tsx`): single entry point for both question-type and lesson-based practice. Selecting lesson(s) only narrows the 4 Vocabulary categories' candidate pool — every other category is unaffected. "开始练习" awaits `fetchQuestionCategory()` for every selected category, then runs `lib/typeSession.ts`'s `selectTypeSessionGroups()` — the one function all 3 `START_QUIZ` sites (Practice, Today's Mission, Special Quest) funnel through, so level-relevance filtering and MCQ-option-shuffling each happen exactly once regardless of entry point. Passage selection is round-robin per category (persisted queue, not pure random) so repeated practice cycles through every passage before repeating.
- **Quiz** (`Quiz.tsx`): steps through the session's groups one at a time; `gradeGroup()` (`lib/grading.ts`) grades MCQ/Fill-in immediately, Long-Answer/Writing-Constrained wait for a self-check click. Auto-advances after 0.8s once every item in a group graded correct outright.
- **Result** (`Result.tsx`): saves history, awards achievements/Special-Quest completions, offers a PDF export for `mode: "type"` sessions — all in one mount-effect guarded by a `ranRef` (not just an empty dep array), since React 18 StrictMode double-invokes mount effects in dev and this logging isn't idempotent.
- **Home** (`Home.tsx`): a dashboard — `PetHeroCard`, `SpecialQuest`, `TodayMission`, a Continue Learning row, `.today-summary-card` (same-day PDF export), `RecentAchievements` (merged achievements+history feed, top 5, no bulk-clear). `PetHeroCard` is deliberately not a `.dash-card` (no boxed background — sits directly on the page).
- **TodayMission**: 3 hardcoded cards (Dictation/Vocab Review/Reading Comprehension) with independent completion checks (`lib/stats.ts`). Completing all 3 in a day pays `MISSION_COMPLETE_BONUS_BP` once (`achievements.ts`'s `checkAndAwardMissionBonus()`, called from `Result.tsx` and all 4 Tingxie completion sites — dedup-guarded so only the first trigger that day pays it).
- **SpecialQuest**: a separate once-a-day wheel (`state/specialQuest.ts`), independent of Today's Mission. Completion is detected at each activity's own site (`PlayGame.tsx`, `PetContext.tsx`'s `applyGrowthAndMood`, `Result.tsx`), each through `completeSpecialQuest()`'s dedup guard.
- **Owl/Shop/Bag**: growth+hunger via `common/PetStatBars.tsx` (hunger = `computeCurrentMood()` — there's no separate hunger stat). Buying (`Shop.tsx`) only adds to inventory; giving/playing an item (`Bag.tsx`) applies its growth/mood effect. Item icon PNGs: note `"puzzle"`'s icon file is `memory.png` (its minigame changed, its `ShopItem.id` didn't, for inventory-key compatibility — `data/pet.ts`'s `shopItemIconPath()`).

### Toy minigames (`src/components/Play/`)
Each toy (`ball`/`kite`/`puzzle`) has a `TOY_GAMES` config (`data/pet.ts`) and its own game component. Tapping a toy in the Bag consumes it from inventory immediately (irreversible even if abandoned) and routes to `"play"`; only a reported completion grants the reward (`GameCompletion { perfect, scoreLabel }` — flat reward always, bonus if perfect). **For any new toy game: drive fall/sweep animation with a remounted (`key={attempt}`) CSS keyframe, not `requestAnimationFrame` + React state** — an earlier rAF version silently stalled for real users (likely a StrictMode-double-effect edge case).

### Read a Story (`src/components/Story/Story.tsx`)
Independent of the Quiz/Result pipeline (no history/achievement hooks) except one: finishing a real (non-placeholder) lesson's last page awards a flat `STORY_COMPLETE_BP_AWARD` once. `StoryReader` is a top-level function, not nested inside `Story()`, so it doesn't remount (and lose its speaking-state) on every parent re-render.

### Tingxie / 听写 (`src/components/Tingxie/`)
Its own local `TingxieProvider` (reducer/Context scoped to this subtree) — leaving the mode resets everything **except** one timestamp (`state/tingxieProgress.ts`, "when did any activity last complete") kept only so Today's Mission can see it after unmount. Four activities per lesson: **Learn** (vocab flip-cards + a sentence-reordering game), **Apply** (fill-in-the-blank flip cards, only for vocab with a `sentenceBank`), **Play** (a 60s timed word-cloud tap game — distractors drawn from *every* lesson's vocab, not just the current one; capped at `TINGXIE_PLAY_CONFIG.DAILY_BP_ROUND_LIMIT` = 3 BP-earning rounds/day as an anti-farming limit, though the round itself always plays normally), **Test** (`Practice.tsx` internally — UI-only rename to "测试 Test", no code renamed). BP is a per-unit rate (`TINGXIE_BP_PER_UNIT`) × items covered that visit, computed once per mount (`useRef`-guarded, so replaying an activity re-earns BP by design) — **except Play**, which earns live per-tap and calls `awardBP()` once (clamped at 0) when its timer ends. Every award site calls the same 3 hooks: `recordTingxieActivityCompleted()`, `logAchievement({ type: "tingxieCompleted" })`, `checkAndAwardMissionBonus()`. Custom review (自由复习, `TingxiePicker.tsx`) pools several lessons into one synthetic session for Apply/Play/Test — Learn is unavailable there (no single "lesson visit" to attach its BP to).

### Pet / BP layer (`src/data/pet.ts` + `src/state/PetContext.tsx`)
`PetProvider` holds `PetState` in `useState`, persisted via `saveAndSync` (see Auth/sync below) on every change. Key invariants:
- **Mood is always derived**, never stored live (`computeCurrentMood()` decays fresh from `moodAtCheckpoint`+`lastFedAt` on every call) — this is what makes time-based neglect work without a server and avoids compounding rounding error.
- **Growth is normally monotonic** (only earned by feeding/play), with one exception: `settleGrowthDecay()` converts whole days spent at 0 mood into lost growth via a `growthDecayCheckpointAt` anchor that only advances once mood is genuinely 0 (no debt silently accrues otherwise). Settled on mount, every 15 min, on tab refocus, and inline before any feed/play.
- **No achievement is ever logged for feeding/playing/evolving the pet** — only learning activity is tracked.
- `giveItem()`/`applyPlayReward()` both return `{ agedUp, age }` (crossing a 100-growth boundary) so callers can play the level-up sound/banner instead of the routine one.

### Owl art / Sound (`OwlArt.tsx`, `src/lib/sound.ts`)
Owl art: one PNG per stage×mood in `public/owl/`, with an optional matching MP4 (`OwlArt.tsx` always tries the video first, falls back to the PNG on `onError` — dropping a new MP4 in just works, no allowlist to update).
Sound: most effects are pooled MP3 playback (`playFile()`, capped pool per sound). **Don't switch back to `new Audio()` per call** — that caused a real mobile-Safari/Chrome memory/lag bug, since `App.tsx`'s global per-click sound listener fires on nearly every tap app-wide. Every sound URL has a `?v=<timestamp>` cache-buster (a replaced MP3 was otherwise served stale indefinitely by the browser cache).

### History, achievements, stats (`src/state/*.ts`, `src/lib/stats.ts`)
- `history.ts` (`HISTORY_KEY`) — last 50 session summaries, deletable individually (no bulk-clear).
- `todaySummary.ts` — today-only, full-detail counterpart (feeds the same-day PDF export); local-only, not synced.
- `achievements.ts` (`ACHIEVEMENTS_KEY`) — up to 30 recent, learning-only types. Dedup differs by type: `missionComplete` once/day, `questionsMilestone` once ever, `storyCompleted`/`specialQuestComplete`/`tingxieCompleted` not deduped here (each caller already guards its own, or genuinely should recur).
- `specialQuest.ts` — local-only, day-scoped.
- `stats.ts` — shared date-bucketing (`dateKey()`, DST-safe local-calendar-day) and Today's Mission completion checks.

### Styling (`src/styles/styles.css`)
Single global stylesheet, "claymorphism" design system (pastel palette, puffy double-shadow cards, pill bars/badges). **Light mode only — don't re-add a `prefers-color-scheme: dark` override without being asked**, it was deliberately removed once already. Tokens live in `:root` (`--primary`, `--gold`, `--correct`/`--incorrect`, the `--shadow-1`/`--shadow-2`/`--shadow-press` pair-shadow trio) — most shared classes already consume these, so a re-theme is mostly a token swap, not a rewrite.

### Auth / cross-device sync (`src/state/AuthContext.tsx`, `src/lib/sync.ts`, `src/lib/supabase.ts`, `src/lib/username.ts`)
Username/password login (Supabase Auth, username mapped to a synthetic `<user>@example.com` — see `lib/username.ts`) that syncs progress across devices on top of the existing localStorage stores, which keep working unchanged for a student who never logs in. Every visitor hits a forced login gate first, with a one-tap "Continue as Guest" escape hatch (`isGuest`, persisted, never re-gates a device once set).

Synced stores (each exports its own `KEY` constant, assembled by `SyncBootstrap.tsx`): `PetContext.tsx`'s `PET_KEY`, `history.ts`'s `HISTORY_KEY`, `achievements.ts`'s `ACHIEVEMENTS_KEY`, `tingxieProgress.ts`'s `TINGXIE_PROGRESS_KEY`, `levelPreference.ts`'s `LEVEL_KEY`. `todaySummary.ts`/`specialQuest.ts` stay local-only (day-scoped, self-resetting anyway).

**Flow** — this area has already caused (and re-caused) real data-loss bugs, so trust `lib/sync.ts`'s own comments over reconstructing the reasoning from scratch if you're changing it:
1. **Login → pull before push.** `setSyncUser(userId)` immediately closes a `syncReady` gate blocking all outbound pushes. `SyncBootstrap.tsx` then runs `pullAndMergeAll()` (per-key last-write-wins by timestamp, retried on failure via `online`/`visibilitychange` until it genuinely succeeds) and only opens the gate (`markSyncReady()`) once that succeeds. A key with no local sync-timestamp at all (written while signed out, i.e. guest play) is never adopted as this account's data just because nothing existed on the server yet to compare it against.
2. **Regular play → debounced push.** Every mutator calls `saveAndSync(key, value)`: writes `localStorage` immediately, debounces (~2s) a background upsert to Supabase's `user_state(user_id, key, value, updated_at)` table. Also flushed early on tab-hidden or reconnect.
3. **Logout → flush before clearing.** `signOut()` `await`s `flushAllNow()` (pushes everything still pending, bypassing the debounce/gate) before the Supabase session actually ends; only then does `SyncBootstrap.tsx`'s sign-out effect wipe local storage back to guest/default state and reset the in-memory sync bookkeeping (`resetSyncState()`), so no leftover pending write from this account can leak into the next signed-in user on the same tab/device.

A brand-new signup (`Auth.tsx`'s `startFresh()`) resets every synced store to default *before* any merge runs, so it never inherits whatever was locally present (guest play, leftover test data) as if it were that new account's progress.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Keep this file current.** Whenever you make a major change — a new screen/mode, a new top-level data file, a new persisted `localStorage` key, a change to the pet/BP economy, or anything else a future session would need to know to avoid rediscovering it from scratch — update the relevant section of this file (or add a new one) as part of that change, not as an afterthought. Small tweaks (copy edits, styling tweaks, bug fixes) don't need an update. When in doubt, ask: "if I started a fresh session tomorrow with no memory of this conversation, would this file tell me the truth about the code?" If not, fix it.

## What this is

A Vite + React + TypeScript web app for practicing Chinese-language exam questions (Primary school Chinese / Higher Chinese, Singapore-style "语文应用": cloze, error correction, reading comprehension, dialogue completion, hanyu pinyin, etc.), with a Tamagotchi-style gamification layer (earn BP for correct answers, hatch and grow a pet owl, feed/play with it via a shop + bag). The app needs no backend and works fully offline once built/served.

## Running / testing

Standard Vite/npm project — no test suite (verify changes by running the dev server and clicking through the flow manually):

- `npm install` — install dependencies (React 19, `@supabase/supabase-js` is present as a dependency for a not-yet-built sync layer, see below).
- `npm run dev` — start the Vite dev server.
- `npm run build` — `tsc -b && vite build`; always run this (or at least `npx tsc -b`) after non-trivial changes, since there's no test suite to catch regressions otherwise.
- `npm run lint` — `oxlint`.
- `npm run preview` — serve the production build locally.

## Architecture

### Data layer (`src/data/`)
- `types.ts` — shared TypeScript interfaces for everything below: `Question` (`MCQQuestion | FillInQuestion | SelfCheckQuestion`), `QuestionGroup`, `Passage`, `GroupResult`/`GroupResultItem`, `HistoryEntry` (`mode`/`categoryCounts` are optional — absent on pre-dashboard-redesign entries, every reader treats a missing value as "no data", never crashes), `PetState` (includes `questionsLifetime`, a lifetime count of individual questions answered, used for the "every 100 questions" achievement), `ShopItem`, `PetStage`, `MoodBucket`, `Achievement`/`AchievementType` (`"missionComplete" | "questionsMilestone"` — deliberately learning-only; feeding/evolving the pet is not tracked as an achievement, see `RecentAchievements` below), and the Tingxie JSON-shape interfaces `TingxieVocabItem`/`TingxieSentence`/`TingxieSentenceBankEntry`/`TingxieLesson`/`TingxieLessonIndexEntry` (see the Tingxie section below).
- `tingxie.ts` — Tingxie's data layer: `fetchTingxieLessonIndex()`/`fetchTingxieLesson()` (the app's only runtime `fetch()`s, cached in module-level `Map`s), `tingxieIconEmoji()`'s icon lookup, sentence/queue-building helpers (`tingxieSentenceWords`, `tingxieBlankWord`, `buildTingxieApplyQueue`, `buildTingxiePracticeVocabQueue`/`buildTingxiePracticeSentenceQueue`, `pooledTingxieReview`), and the `TingxieApplyItem`/`TingxiePracticeItem` queue-item types.
- `stories.ts` — "Read a Story" mode's data: `StoryLesson`/`StorySegment`, `segmentSentences()`, and `STORY_LESSONS` (`Record<number, StoryLesson>`, one entry per lesson `1..LESSON_COUNT`). Bundled as plain TS data (unlike Tingxie's fetch-on-demand JSON) since a story passage is small — no need for the runtime-fetch pattern. A `StoryLesson.segments[]` entry is one **page**, not one paragraph — `StorySegment.paragraphs: string[][]` groups one or more of the original story's paragraphs onto that page (each inner array is one paragraph's sentences) so every page has **at least 3 sentences**; a short paragraph gets merged onto a neighboring page rather than left alone as a sparse page, while paragraph boundaries themselves are always preserved (each still renders as its own `<p>` in `Story.tsx`, see the Read a Story section below). `segmentSentences(segment)` flattens a page's paragraphs into one sentence list for call sites that don't care about paragraph boundaries (the page-level dictation button). Every sentence is **hand-split at authoring time**, not by a runtime regex — Chinese dialogue punctuation (a “…” quote spanning multiple sentence-ending marks) doesn't split cleanly with a generic rule, so sentence boundaries are a one-off authorial choice baked into the data (see Lesson 1 for the convention: a quote that opens mid-sentence and doesn't close until the end of its own following sentence is still split at each 。！？, even though a sentence's closing quote mark ends up on the *next* chunk — harmless for read-aloud, since TTS doesn't vocalize quote glyphs differently anyway). Only Lesson 1 has a real story today (the full passage, paginated into 6 pages); `placeholderLesson(id)` fills lessons 2-17 with a one-page "coming soon" stub (not held to the 3-sentence-per-page guideline, it's stub content) and `placeholder: true` (read by `Story.tsx`'s lesson picker to show a "敬请期待" badge) — replace a lesson's entry in `STORY_LESSONS` with real `segments` to add its story, no other file needs to change.
- `questions.ts` — the question "database". This is the file to edit when adding/editing practice content:
  - `LESSON_COUNT` — number of lessons shown in the Practice screen's lesson picker.
  - `CATEGORIES` — map of category key → `{ label, lessonMode }`. `lessonMode: true` categories are single-sentence items eligible for lesson-filtering; `lessonMode: false` are passage-based items that never take a lesson filter.
  - `VOCABULARY_CATEGORY_KEYS` — `["pinyin", "vocab", "phrase", "usage"]`, the 4 categories the Practice screen combines into one "词语运用 Vocabulary" button — also exactly the set whose `lessonIds` were actually verified against a real per-lesson vocab list (see the `lessonIds` note below), which is why lesson-filtering only ever applies to these four.
  - `SUBJECTS` — e.g. `["Chinese", "Higher Chinese"]`, used as a filter on the Practice screen.
  - `CATEGORY_SUBJECTS` — `Record<category, Set<subject>>`, computed once from `QUESTION_GROUPS` itself (not hand-maintained) — which subjects actually have at least one group of each category. Higher Chinese currently only has `cloze`/`errorcorrect`/`comprehension`; every other category (including all of Vocabulary's four) is Chinese-only. `Practice.tsx` uses this to grey out/disable question-type buttons that don't exist for the selected subject, and `state/AppStateContext.tsx`'s `SELECT_SUBJECT` reducer case uses it to drop any already-selected category that the newly-picked subject doesn't have (so a stale selection can't sit there invisibly still counting toward the session).
  - `QUESTION_GROUPS` — array of all groups. A **group** is either a standalone question (`passage: null`) or a passage plus every question that shares it — always presented and graded together, never split apart. Each has `groupId`, `subject`, `paper`, `section`, `category`, `lessonEligible` + `lessonIds`, `passage`, an optional shared `optionBank` (e.g. dialogue completion — rendered once, questions reference option keys instead of repeating them), and `questions[]` (`qNo`, `marks`, `format`, `text` — supports `__word__` markers rendered as underlined spans via `RichText`/`richText.tsx` — plus format-specific fields: MCQ has `options`/`correctKey`, Fill-in has `accepted`/`displayAnswer`, Long-Answer/Writing-Constrained just has `displayAnswer` and is self-graded by the student).
  - To add a new paper/lesson: append new group objects following an existing group's shape. Bump `LESSON_COUNT` for a new lesson number; add keys to `CATEGORIES` for a new question type. No other file needs to change for new data of the existing shape.
  - **How `lessonIds` gets assigned, and why it differs by category.** For `pinyin`/`vocab`/`phrase`/`usage`, `lessonIds` is verified against each lesson's actual taught-vocabulary list: the "tested word" is extracted per format (the `__word__` marker for pinyin/phrase, the correct MCQ option's text for vocab, or the `（词语：X）` label — or, absent that label, the substring common to all 4 option sentences — for usage) and matched against a real per-lesson vocab list to find which lesson actually teaches that word. A word taught in two lessons gets both lesson numbers in `lessonIds` (recycled vocab); a word not found in any lesson's list gets `lessonEligible: false` instead of a guessed lesson. This was last done as a one-off pass (not an ongoing script) matching 178 questions against a 17-lesson vocab list the user supplied — see git history around the "practice by lesson" retagging commit for the exact method. `conjunction` and `sentence` questions have **no such verification** — there's no single tested vocabulary word to match against a list, since these test connector words (关联词, e.g. 要是……就/不但……而且) or sentence-logic completion, not a specific taught word. Their `lessonIds` is just **whichever lesson number the source exam paper as a whole was assigned** (all of a paper's lesson-eligible questions share one `lessonIds` value, e.g. every CH-paper question got `[1]`, every NH-paper question got `[2]`, etc.) — content-blind, and likely just as inaccurate as pinyin/vocab/phrase/usage were before that pass. Fixing it would need a different reference (which conjunction pairs are taught in which lesson), not a vocab list.
- `pet.ts` — pet/BP tunable config (not per-user state): `PET_STAGES` (6 growth stages: egg/baby/toddler/young/teenager/adult, with `minAgeYears` thresholds — 0/3/7/11/16/21), `GROWTH_PER_AGE_YEAR` (100 — see the age note below), `MOOD_DECAY_PER_HOUR`, `BP_AWARD` (per question format), `TINGXIE_BP_AWARD` (per Tingxie activity — see the Tingxie section below), `MISSION_COMPLETE_BONUS_BP` (one-time-per-day bonus for finishing all 3 Today's Missions — see `TodayMission` in the Screens section), `SHOP_ITEMS` (id/cost/growth/mood — a toy's `mood` is its *maximum* possible payout, see `TOY_GAMES` and the Toy minigames section below), `TOY_GAMES` (one minigame config per toy `ShopItem.id`, see below), `PET_DEFAULT_STATE`, and the owl-art helpers described below.
  - **Age**: purely a derived display/evolution concept, never stored — `state/PetContext.tsx`'s `getAge(growth)` is `Math.floor(growth / GROWTH_PER_AGE_YEAR)`. Growth itself is unchanged (still only earned by feeding, via `giveItem()`, exactly as before); age is just a friendlier framing of the same number (100 growth = 1 "year"), and `getStage()`/`nextStage()` now compare age against each `PetStage.minAgeYears` instead of comparing raw growth against a raw threshold. This made stage thresholds ~10x larger in growth-point terms than before (adult used to be 200 growth, now 2100 = 21 years × 100) — feeding paces/item costs are unchanged, so reaching Adult now takes proportionally longer. Shown next to the stage label on the Owl screen and `PetHeroCard` (e.g. "🎂 4岁"). **Deliberately not shown**: how many years until the next stage — the growth bar (`PetStatBars`, `PetHeroCard`) only ever shows progress within the *current* age year (`growth % GROWTH_PER_AGE_YEAR`, always 0-100), never `PetStage.minAgeYears`, so a curious kid can't read off exactly when the next evolution lands. Every time growth crosses a 100-point boundary (`giveItem()`'s returned `agedUp`), `Bag.tsx` plays `Sound.levelUp()` and shows a celebratory age-up banner — see the Bag bullet below and Sound section.

### App state layer (`src/state/AppStateContext.tsx`)
`useReducer` + two React Contexts (`AppStateCtx`/`AppDispatchCtx`, read via `useAppState()`/`useAppDispatch()`). `AppState` holds `screen` (`"home" | "practice" | "quiz" | "result" | "owl" | "shop" | "bag" | "play" | "tingxie" | "story" | "auth"`), the current quiz session (`mode`, `modeLabel`, `groups`, `groupIndex`, `results`, `submitted`), picker selections (`selectedSubject`, `selectedCategories`, `selectedLessons`), and `playingItemId` (which toy's `ShopItem.id` is active on the `"play"` screen — see the Toy minigames section below). `App.tsx`'s `ScreenRouter` switches on `state.screen` to render the matching component from `src/components/`. `"auth"` is a routed-to placeholder for a not-yet-built login screen. `"story"` is the sole entry point into Read a Story (`Story.tsx`) — like Tingxie, everything past that (which lesson, which page) is local `useState` inside `Story.tsx`, not further `AppState`/actions; unlike Tingxie it doesn't even need its own reducer/Context, since the local state is just two numbers (see the Read a Story section below).

Quiz session actions: `START_QUIZ`, `SUBMIT_GROUP`, `UPDATE_ITEM_RESULT` (patches one self-check item's result in place after the student clicks a self-check button — see below), `NEXT_GROUP`, `RESET_TO_HOME` (mirrors the old app's `resetToHome()`: clears session state but keeps `selectedSubject`/`selectedCategories`/`selectedLessons`). `START_PLAY` (sets `screen: "play"` + `playingItemId`, dispatched from `Bag.tsx` when a toy's "Play" button is clicked — see the Toy minigames section below).

Picker actions: `TOGGLE_CATEGORY` (single category key), `TOGGLE_CATEGORY_GROUP` (an array of keys, toggled as one unit — all-selected → deselect all, otherwise select all; used by `Practice.tsx`'s combined "词语运用 Vocabulary" button, see below), and `SET_CATEGORIES` (full replace — used by Today's Mission's "复习一课 Revise a Lesson" to jump straight to a clean Vocabulary-only selection). `SELECT_SUBJECT` also prunes `selectedCategories` down to only categories `CATEGORY_SUBJECTS` (`data/questions.ts`) says exist for the newly-picked subject, so switching to Higher Chinese silently drops an already-selected Chinese-only category instead of leaving it selected-but-greyed-out.

Lesson-filter actions: `TOGGLE_LESSON`/`SELECT_ALL_LESSONS` toggle `selectedLessons: Set<number>`, where **empty means "all lessons"** (the default — no filter) rather than "none". Any action that changes `selectedCategories` (`SELECT_SUBJECT`, `TOGGLE_CATEGORY`, `TOGGLE_CATEGORY_GROUP`, `SET_CATEGORIES`) also resets `selectedLessons` back to empty whenever the result no longer has all of `VOCABULARY_CATEGORY_KEYS` selected (`vocabRetained()` helper) — a lesson filter left over from a since-deselected Vocabulary would otherwise sit there silently.

### Screens (`src/components/`)
Each top-level screen is its own component/folder: `Home`, `Practice`, `Quiz`, `Result`, `Owl`, `Shop`, `Bag`, `Play`, `Tingxie`, `Story` (see below). Shared UI lives in `components/common/`: `Modal.tsx` (`ConfirmModal` — a custom in-page confirm dialog, used instead of `window.confirm` so styling/behavior stays consistent, e.g. leaving a quiz mid-session or clearing history), `OwlArt.tsx` (see Owl art below), and `TopNav.tsx` (see below).

- **`common/TopNav.tsx`**: a persistent top nav (`.top-nav`, `position: sticky; top: 12px`), plain Chinese-only text labels (no icons/English subtitles) with 5 items — 主页 Home (`RESET_TO_HOME`, same as every other "back to home" affordance in the app), 听写练习 (→ `"tingxie"`), 练习 Practice (→ `"practice"`), 读故事 Read a Story (→ `"story"`), 宠物 Pet (→ `"owl"`, and stays highlighted while on `"shop"`/`"bag"`/`"play"` too, since those are reached from the pet flow). `App.tsx`'s `ScreenRouter` renders it above every screen **except** `"quiz"`/`"result"` — a quiz in progress already has its own Home button with a "leave without saving?" confirmation (see the Quiz bullet below), and an always-visible second way to navigate away would either bypass that confirmation or need to duplicate it, so it's simplest to just not show it there.

- **Practice** (`Practice.tsx`, screen `"practice"`): the single entry point for both question-type and lesson-based practice (previously two separate screens/pickers — merged into one). Top section "选择题型 Select Question Type" is unchanged from the old Type Picker: a subject row (All/Chinese/Higher Chinese chips) and a `category-grid` of `TYPE_PICKER_GROUPS` buttons (Pinyin/Vocabulary/Phrase Meaning/Correct Usage combined into one "词语运用 Vocabulary" button via `TOGGLE_CATEGORY_GROUP`, every other category its own button), each greyed out/disabled (`.category-disabled`) when `groupApplicable()` says none of its categories exist under the selected subject (backed by `CATEGORY_SUBJECTS`). Below that, a "选择课文 Select Lesson(s)" section — a `.lesson-grid` of chips (an "全部课文 All Lessons" chip plus one per `LESSON_COUNT`, each showing how many Vocabulary-category questions match under the current subject, greyed out at 0) — is only interactive once Vocabulary's 4 categories are all selected (`vocabularySelected`); otherwise every lesson chip is `disabled` and a `.picker-hint` explains why. Selecting specific lesson(s) restricts *only* the Vocabulary categories' candidate pool to groups whose `lessonIds` include one of the chosen lessons — every other selected category (conjunction, sentence, cloze, ...) is completely unaffected by the lesson filter, since only Vocabulary's `lessonIds` were verified against a real vocab list (see the `lessonIds` note above). "开始练习 Start Practice" runs the exact same `selectTypeSessionGroups()` sampling as before (one random passage per passage-category, individual categories pooled and capped) — a lesson filter only narrows Vocabulary's candidate pool going into that function, it doesn't change how many questions come out. The resulting session's `mode` is `"lesson"` only when the student genuinely narrowed away from the "all lessons" default (`selectedLessons.size > 0`); otherwise it's `"type"`, same as a plain type-only session — this is what keeps Today's Mission's "复习一课 Revise a Lesson" (`isLessonMissionComplete`, checks for a `mode: "lesson"` history entry today) working without any change to that check.

- **Quiz** (`Quiz.tsx`): groups for the session are shuffled once (`lib/shuffle.ts`) and stepped through one at a time via `state.groupIndex`. Submitting a group calls `gradeGroup` (`lib/grading.ts`), which grades MCQ/Fill-in immediately and returns self-check items (Long-Answer/Writing-Constrained) as `correct: null` until the student clicks a "✓ 我答对了 / ✗ 还需加强" button, which dispatches `UPDATE_ITEM_RESULT`. Each question has a "🔊 听写 Dictation" button (`lib/speech.ts`'s `speakText()`, `SpeechSynthesisUtterance` in `zh-CN`) that reads the question aloud; a group with a passage (`group.passage`, i.e. Cloze/Error Correction/Comprehension/Dialogue/Practical Text) additionally shows its own dictation button in the passage box's header (`.passage-head`, rendered by the `PassageBox` sub-component) that reads the full passage text, separate from each question's own button — since passages run long, this button toggles into a "⏹ 停止 Stop" button (`speakText()`'s optional `onDone` callback, fired whether the reading finishes naturally or is interrupted) rather than just firing once like the per-question buttons. `speakText()` always `cancel()`s any prior utterance before starting a new one, but that alone doesn't stop a reading that's still playing when the student just moves on without triggering new speech; `Quiz.tsx` additionally calls `speech.ts`'s `stopSpeaking()` explicitly in `handleSubmit()` and on every `state.groupIndex` change/unmount, so a reading never bleeds into a question the student has already left. **Auto-advance:** if every item in a submitted group graded `correct === true` outright, the quiz auto-dispatches `NEXT_GROUP` after a 0.8s pause (with a visible "moving on..." hint on the Next button); anything wrong/skipped, or still awaiting a self-check click, requires the manual click. A pending auto-advance is cancelled if the student clicks Next early or navigates to a new group.
- **Result** (`Result.tsx`): computes the session score, saves it to history (`state/history.ts`, including `mode`/`categoryCounts` for the dashboard below) once on mount, plays `Sound.applause()` on a score of 90% or higher or `Sound.encourage()` otherwise, and — in the same once-per-mount effect — calls `usePet().recordQuestionsCompleted()`, logs any newly-crossed `questionsMilestone` achievement, and calls `state/achievements.ts`'s `checkAndAwardMissionBonus()` (see `TodayMission` below). The effect is guarded by a `ranRef` (not just an empty dep array) because React 18 StrictMode double-invokes empty-dep effects once on mount in dev, and unlike the old idempotent `saveHistory`-only version, achievement logging is not idempotent. For `state.mode === "type"` sessions only, also shows a "🖨️ 打印 / 存为 PDF Print / Save as PDF" button (`lib/exportPdf.ts`'s `exportSessionToPdf()`) that renders the whole session (passages, word banks, every question with the student's answer vs. the correct/model answer) into a **new tab** (`window.open("", "_blank")`, called synchronously in the click handler to dodge popup blockers) and calls `print()` on it after a short `setTimeout`, so the student saves it via the browser's print dialog — deliberately not a PDF-generation library, to avoid embedding a CJK font just for Chinese text. Used to write into a hidden 0×0 `<iframe>` instead; switched to a real new tab because iOS/iPadOS Safari does not reliably fire `print()` on a hidden iframe's `contentWindow` (the dialog silently never opens) — don't revert to the iframe approach. This is what `GroupResultItem.answer` (`data/types.ts`) exists for: `lib/grading.ts`'s `gradeQuestion()` now keeps the student's raw MCQ key / typed text on the result item instead of discarding it after grading.
- **Home** (`Home.tsx`): a dashboard, not just a mode picker. Top to bottom: `PetHeroCard` (see below — this is the first section, no separate greeting above it), `TodayMission`, the Continue Learning section (three `.mode-card` mode-picker buttons, **Dictation Practice first**, then the combined Practice screen, then Read a Story — `.mode-cards` is `grid-template-columns: repeat(auto-fit, minmax(180px, 1fr))`, not a fixed 2-column grid, specifically so a 3rd card doesn't dangle alone on its own row), the `.today-summary-card` (see below), then `RecentAchievements` — the dashboard's last section.
- **`.today-summary-card`** (inline in `Home.tsx`, no separate component file): a "🖨️ 打印 / 存为 PDF Print / Save as PDF" button for `lib/exportPdf.ts`'s `exportTodaySummaryToPdf(hist)` — a same-day aggregate PDF, distinct from Result.tsx's single-session one. Only rendered when there's something to show (`getTodayStats(hist).questions > 0 || isTingxieMissionComplete()`), so an empty dashboard doesn't offer a pointless button. See `state/todaySummary.ts` below for what feeds it.
- **`PetHeroCard.tsx`**: the pet art is the centerpiece, not a small thumbnail beside stats — and the greeting that used to be Home's own separate top section (`greeting()`'s time-of-day text + a `getTodayStats(hist)`-derived subgreeting) is now *merged into this card* rather than living above it, so the greeting and the pet read as one visual unit. Takes `hist: HistoryEntry[]` as a prop (same pattern as `TodayMission`/`RecentAchievements`) purely to compute that subgreeting. The whole card is one `<button>` navigating to the Owl screen (no separate Feed button; the Owl screen's own Feed button already does the inventory-aware Bag-vs-Shop routing). It's deliberately **not** a `.dash-card` (no boxed background/shadow of its own; sits directly on `.home`'s plain background, unlike every other dashboard section — `.home` itself overrides `.screen`'s boxed gradient panel back to `background: none; border-radius: 0` for the same reason, so there's no single outer "everything card" wrapping the whole dashboard either), and is manually opted into the dashboard's fade-in-on-load animation (`dash-card-in`) since it can't inherit that from `.dash-card`.
  - **Layout**: `.pet-hero-row` is two columns, both sharing `flex: 1 1 200px; max-width: 300px` so they grow together and land at roughly equal widths (any leftover space past both caps just trails after the right column, via `margin-left: auto` on `.pet-hero-right`, rather than stranding itself mid-row) — `align-items: flex-start`, not `center`, since the left column runs taller than the right. **Left** (`.pet-hero-left`): `.pet-hero-welcome` (the merged-in greeting — `.pet-hero-greeting`/`.pet-hero-subgreeting`, smaller type than the old standalone `.home-greeting`/`.home-subgreeting` since it's squeezed into this narrower column now), then `.pet-hero-identity` (name + stage badge, stacked — no BP badge here anymore), then `.pet-hero-bars` (growth/hunger, stacked label-above-value so it still reads at its narrow end; no `flex`/`max-width` of its own since it's a stacked child of `.pet-hero-left` now, not a row item — those properties would target the wrong axis). **Right** (`.pet-hero-right`, `align-items: flex-end`): the BP badge (`.pet-status-bp`) on top, then `.pet-hero-art-col` (`width: 100%` of the column) containing a big `owl-hero`-sized sprite (`width: 100%; max-width: 300px; aspect-ratio: 1` — fills its column rather than being capped by a `vw` formula that undershoots once the container is wider than the viewport-relative cap) — bigger than `owl-large` on the dedicated Owl/Bag screens — with a static radial-gradient glow behind it via `::before`, plus the speech bubble (`max-width: min(240px, 90%)`).
  - **`.pet-hero-stage-badge` overrides `white-space: normal`** (every other badge sharing that shared rule group — `.marks-badge`/`.quiz-bp-badge`/`.pet-status-bp`/`.stat-tile-badge` — stays `nowrap`): its text ("蛋 Egg · 🎂 0岁 · 第 1／6 阶段") is long relative to `.pet-hero-left`'s narrow column, and since this card has no `.dash-card` box with `overflow` clipping, an overflowing `nowrap` pill wouldn't get cut off visibly — it would silently paint underneath the art column instead, invisible rather than obviously broken. Let it wrap instead.
  - Several earlier layouts, don't reintroduce: a side-by-side small-art-thumbnail-plus-stats card; a vertical stack with the bars full-width *below* the art; a row where both sides were capped at small fixed/`vw`-relative sizes leaving a large empty gap between them on anything wider than a phone; a row where the art's cap was noticeably larger than the bars'; the BP badge top-aligned with the name instead of centered with the stage badge, and later top-aligned with the stage badge instead of living in the right column above the art; and a standalone greeting section living *above* this card instead of merged into its left column.

- **TodayMission** (`TodayMission.tsx`): three hardcoded, always-clickable `.mission-row` buttons (deliberately not a data-driven list — with only 3 missions that have genuinely different completion checks and click behaviors, hardcoding is simpler than a small-list abstraction). "复习一课 Revise a Lesson" is done-today if any `mode: "lesson"` history entry exists for today (`lib/stats.ts`'s `isLessonMissionComplete`); clicking it (`startLessonMission()`) resets subject to "All", replaces `selectedCategories` with just Vocabulary (`SET_CATEGORIES`), resets `selectedLessons` to the "all lessons" default (`SELECT_ALL_LESSONS`), then navigates to the Practice screen so the student picks which lesson(s) themselves — Practice is what actually tags the resulting session `mode: "lesson"`, once the student narrows away from "all lessons" (see the Practice bullet above). "阅读练习 Reading Practice" is done-today if at least one group from `READING_MISSION_CATEGORIES` (`cloze`/`comprehension`/`dialogue`/`practical` — deliberately excludes `errorcorrect`) was completed today (`getReadingMissionCount`); clicking it randomly picks 2 of those 4 categories and immediately starts a quiz (`selectTypeSessionGroups`, same as Practice would build), no picker screen shown. "听写练习 Dictation Lesson" is done-today if the student completed *any one* of Tingxie's three activities today — Learn's vocab flip-through, Learn's sentence game, Apply, or Practice (`lib/stats.ts`'s `isTingxieMissionComplete`, backed by `state/tingxieProgress.ts`'s `recordTingxieActivityCompleted()`/`getTingxieLastCompletedAt()`, the one small piece of Tingxie progress that *is* persisted — see the Tingxie section); clicking it navigates straight into Tingxie mode. - **RecentAchievements** (`RecentAchievements.tsx`): a single merged, reverse-chronological feed — this used to be two separate dashboard sections ("Recent Achievements" + a "Recent Sessions" history table with its own `.dash-card`); they're now one card under one heading, since a raw log of pet-feeding/leveling events and a raw log of quiz sessions are both just "things that happened," and the app only needs to surface *learning* activity, not pet-interaction history (feeding/evolving the pet is intentionally not tracked or shown at all — see the `AchievementType` note above and the `giveItem()` note below). Takes `hist: HistoryEntry[]` plus `onDeleteRow(id)`/`onClearAll()` callbacks (Home.tsx still owns the `pending`/`ConfirmModal` delete-confirmation state, same as before the merge) as props. Internally loads `state/achievements.ts`'s `loadAchievements()` itself (same self-contained pattern as before), builds one `FeedRow[]` by mapping achievements (`missionComplete`/`questionsMilestone`, each rendered with a bilingual description + `lib/stats.ts`'s `formatRelativeTime()` — defensively filtered to just those two types in case a pre-merge browser still has old `"fed"`/`"evolved"` entries sitting in `localStorage`) and `hist` entries (rendered as a mode label + score, each with a delete "✕" button) into the same row shape, sorts the combined list by date descending, and shows the top 8. Renders `null` when the combined list is empty. The "🗑 清除全部 Clear All" button (`state/history.ts`'s `clearAllHistory`, wired through `onClearAll`) only shown/only clears when `hist.length > 0` — it clears session history, not the underlying achievement log (there's no delete UI for individual achievements).
- **Owl** (`Owl.tsx`): shows growth stage, mood label, and BP, plus `PetStatBars` (see `common/PetStatBars.tsx` below) for the growth and hunger progress bars. The screen's `<h1>` *is* the owl's name (inline-editable via a pencil button, `renameOwl()`) — there's no separate static title. Links to Shop and Bag (with a live bag-item count).
- **Shop** (`Shop.tsx`): spend BP on `SHOP_ITEMS`; buying calls `buyItem()` (adds to the pet's bag, does **not** apply the effect immediately) and animates the purchased item's emoji flying from its card into a bag-count badge (`lib/throwAnimation.ts`'s `flyItemTo`). `ShopItemCard` ("Items for Sale") shares the same "icon + name/stat row" look as `BagItemCard` (see below) — a `.bag-item-row` (icon, Chinese name, one stat line) sits above the card's own "💡 cost BP" Buy button, since purchasing needs a distinct action the row itself can't express. Food's stat line is `🌱 成长 +growth　🍚 饱食度 +mood` — the item's `mood` field is labeled "饱食度 Hunger" (not "心情 Mood") specifically so it reads as feeding the same hunger number the pet's bars show, per the "mood *is* hunger" note below; toy's stat line is `🍚 饱食度最高 +mood` (see the Bag bullet below for why). The screen's read-only "My Bag" preview list reuses the bare `.bag-item-card` class as a plain non-interactive `<div>` (icon + Chinese name only, no stat line) — same terse styling as the tappable Bag cards, just not clickable here.
- **Bag** (`Bag.tsx`): lists bagged items, with `PetStatBars` shown under the owl art (same growth/hunger bars as the Owl screen, so a student can see both stats while feeding, not just after). Each `BagItemCard` is itself a `<button>` (`.bag-item-card.bag-item-card-tappable`) — the whole card is the tap target, feed/play on a single tap, no separate "Give"/"Play" button nested inside it. `Shop.tsx` reuses the bare `.bag-item-card` class for its own read-only bag preview as a plain non-interactive `<div>` (see above), which is why the button-only styling (`cursor: pointer`, `:active` press, `:disabled` state) lives in the `-tappable` modifier rather than the shared base class. Layout is a row (`.bag-item-card`/`.bag-item-row` both set `display: flex; flex-direction: row`) — the emoji sits to the **left** of the name, not stacked above it — with a `.bag-item-info` column (name, then one stat line) to its right; a quantity badge (`.bag-item-qty-badge`, only rendered when `qty > 1`) pins to the emoji's corner rather than its own text line. Cards are deliberately terse — the item's **Chinese name only** (`item.label.split(" ")[1]` — every `SHOP_ITEMS` label is `"<emoji> <Chinese name> <English words>"`, and the Chinese name is always exactly one space-delimited token), no English text, no "tap to feed/play" hint line; the tap affordance comes from the card being a real button, not a label. Food cards' stat line is `🌱 成长 +growth　🍚 饱食度 +mood` (added so a student deciding what to feed doesn't have to remember the item's stats from the Shop visit); tapping one flies the item's emoji from its card onto the owl art (`flyItemTo`) and only calls `giveItem()` (which applies growth/mood and decrements inventory) once the animation lands. `giveItem()` returns `{ agedUp, age }` — `agedUp` is true whenever that give crossed a 100-growth age-year boundary (see the Age note in the Pet/BP layer section below; a stage evolution is always also an age-up, so this one flag covers both) — and `agedUp` decides which sound plays, `Sound.levelUp()` vs the routine `Sound.gift()`. On `agedUp`, `Bag.tsx` also shows a `.age-up-banner` ("🎉 ... 现在是 X 岁了 / now X years old") that pops in once and then stays on screen for as long as the student remains on the Bag screen — cleared only on navigating away (component unmount), not on a timer — this is the *only* place the pet's current age is celebrated; how many years a stage takes is deliberately never shown (see below). Toy cards' stat line is just `🍚 饱食度最高 +mood` (since a toy's payout isn't guaranteed, and every toy's `growth` is 0 anyway so there's nothing else worth showing) — tapping one calls `usePet().consumeItem(item)` (removes it from the Bag immediately, no throw animation) and dispatches `START_PLAY`, handing off to the Play screen; see the Toy minigames section below for what happens next.
- **`common/PetStatBars.tsx`**: shared presentational component rendering two progress bars from a `PetState` — growth and hunger (`computeCurrentMood`, `.mood-bar`/`.mood-bar-fill` classes, gold-toned to read as distinct from growth's primary-color gradient). "Hunger" in the UI is `computeCurrentMood()`'s value — the app has no separate hunger stat; mood *is* what feeding replenishes, so the bar is just a more legible presentation of the existing mood number alongside its `sad`/`neutral`/`happy`/`very_happy` label. The growth bar (`.growth-bar`/`.growth-bar-fill`) deliberately shows progress **within the current age year only** (`pet.growth % GROWTH_PER_AGE_YEAR`, always out of 100) — never progress toward the next evolution stage, and never reveals a `PetStage.minAgeYears` value; how long each stage takes is meant to stay a surprise. `PetHeroCard.tsx` (Home) duplicates this same within-year math for its own bar layout rather than reusing this component. Used by both `Owl.tsx` and `Bag.tsx` so the two stats stay visible on both pet-focused screens.

### Toy minigames (`src/components/Play/`)
Playing with the pet, as opposed to feeding it: each of the 3 toy `SHOP_ITEMS` (`ball`/`kite`/`puzzle`) has a matching minigame config in `data/pet.ts`'s `TOY_GAMES` (keyed by `ShopItem.id`) instead of the flat instant-mood effect food items get. Reached only from `Bag.tsx`'s toy cards (see the Bag bullet above) — there's no Play entry point from the Shop.

- **Flow**: tapping a toy card in the Bag calls `usePet().consumeItem(item)` (removes it from inventory right away — same "irreversible once started" rule as feeding, so abandoning the game mid-play still costs the item, no refund) and dispatches `START_PLAY`, which routes to `"play"` (`PlayGame.tsx`). `PlayGame` looks up the item + its `TOY_GAMES` config and renders the matching game component (`components/Play/types.ts`'s `GameProps`), passing it `onComplete(result: GameCompletion)` and `onExit()`. `onExit` (the game's back button) just navigates back to `"bag"` with no reward — the item's already gone, matching the "consumes regardless of outcome" decision. `onComplete` is the only path that grants a reward.
- **`GameCompletion` contract** (`components/Play/types.ts`): every game reports `{ perfect: boolean; scoreLabel: string }` regardless of what it internally measures — a round-based game (hits out of attempts) and a timed game (elapsed seconds) compute "was this a bonus-earning run" very differently, but both collapse to the same two fields, so `PlayGame.tsx` never needs to know which kind of game produced them. `scoreLabel` is just for display on the result screen (e.g. `"5 / 5"` vs `"0:38"`).
- **Reward math** (`PlayGame.tsx`'s `handleComplete`): flat completion reward always applies once a game reports completion at all (`config.flatMood`, regardless of how close to "perfect" it was); a `perfect: true` result adds `config.bonusMood` on top. `flatMood + bonusMood` always equals the toy's `ShopItem.mood` (its Shop/Bag "max" stat), so the toy economy didn't need rebalancing when this replaced the old instant-give. `usePet().applyPlayReward(item, moodReward)` applies growth (0 for every toy today) + the computed mood and returns `{ agedUp, age }`, same shape as `giveItem()` — `PlayGame` shows the same kind of age-up messaging inline in its result card (not `Bag.tsx`'s `.age-up-banner`, since the student isn't on the Bag screen at that moment) rather than reusing it. `Sound.applause()`/`Sound.encourage()` play on a perfect vs. non-perfect result, same semantics as a Quiz/Tingxie session scoring ≥90%/<90%.
- **`TOY_GAMES` has two config shapes** sharing one flat (non-discriminated-union) `ToyGameConfig` interface: round-based games (`attempts`/`bonusThreshold`) and the timed memory game (`pairCount`/`bonusTimeSeconds`). Every field but the common `flatMood`/`bonusMood`/`bonusLabel` is optional on the type, and each game component reads the ones that apply to its own `game` id with a non-null assertion (`config.attempts!`, etc.) — the fields are never actually missing for a real toy's config, this is just what keeps one `Record` type instead of a discriminated union with per-game prop narrowing at the `PlayGame.tsx` `switch` call sites.
- **`ball` → `CatchGame.tsx`** (`config.game === "catch"`): the marker sweeps back and forth across a track via a plain CSS keyframe animation (`.catch-marker`/`@keyframes catch-sweep` in styles.css), restarted each round by remounting the marker element with `key={attempt}` (a fresh `animationDuration` per round is what ramps up the difficulty) — deliberately **not** a `requestAnimationFrame` + React state loop driving the position; an earlier version did that and the marker silently stalled/never appeared to move for real users, an easy failure mode for a per-frame state loop (e.g. a StrictMode double-effect edge case) that a pure CSS animation isn't subject to. Tap "🎾 接住！Catch!" while it's inside a randomly-placed highlighted zone — hit detection reads the marker's actual on-screen position at tap time (`getBoundingClientRect()`) rather than any JS-tracked position, so it can never drift out of sync with what's rendered. `config.attempts` (5) rounds, `config.bonusThreshold` (5, i.e. a genuine 5/5) for the bonus.
- **`kite` → `FeatherGame.tsx`** (`config.game === "feather"`): one feather at a time falls from a random x position (same CSS-keyframe-restarted-by-remounting-with-`key={attempt}` pattern as `CatchGame`'s marker, see above — a fresh `animationDuration` per round ramps up the fall speed). Unlike the ball game, there's no separate "Catch!" button — the falling feather (a `<button>`) *is* the tap target, so tapping it early is always a hit; letting its fall animation finish untapped (`onAnimationEnd`) is an automatic miss. Both paths resolve through one `resolve(isHit)` guarded by `lockedRef` so a tap and a same-instant natural animation-end can't both score the round. `config.attempts` (8) rounds, `config.bonusThreshold` (7, i.e. 7 or 8 of 8) for the bonus.
- **`puzzle` → `MemoryGame.tsx`** (`config.game === "memory"`, `ShopItem.id` deliberately still `"puzzle"` even though the game itself is now a card-matching memory game, not a leaf-picking guess — keeps existing bagged/purchased inventory keys valid): `config.pairCount` (6) pairs, 12 cards total in a 4x3 grid, flipped via a 3D `perspective`/`rotateY` card-flip (`.memory-card`/`.memory-card-face`, same visual technique as Tingxie's flip cards). Flip two at a time; a match (`Sound.ding()`) stays face-up permanently, a mismatch (`Sound.miss()`) flips back after `MISMATCH_PAUSE_MS` (800ms). There's no fail state — the deck is always eventually solved — so completion (a `useEffect` watching `matchedPairs`, guarded by `doneRef` so it only fires once) always earns the flat reward; a live timer (`elapsedMs`, ticked every 200ms from a `performance.now()` start captured on mount) decides `perfect` via `config.bonusTimeSeconds` (20s) instead of a hit count, reported as the `mm:ss` `scoreLabel`.
- **`PlaceholderGame.tsx`** is a pure fallback (every current toy has a real game) for any future `TOY_GAMES` entry added before its game component exists — claims the flat reward only (`onComplete({ perfect: false, scoreLabel: "—" })`) rather than leaving a purchase wasted, wired in `PlayGame.tsx`'s `switch` `default` case.
- **Shared round-UI CSS** (`.play-round-progress`/`.play-round-feedback*`/`.play-round-hits` in styles.css): the "round N / total", hit/miss feedback line, and running hit/match tally are visually identical across `CatchGame`/`FeatherGame`/`MemoryGame`, so all three render some subset of these shared classes — only the "arena" in between (`.catch-track`/`.catch-marker`/`.catch-zone`, `.feather-sky`/`.feather-target`/`.feather-ground`, or `.memory-grid`/`.memory-card`) is game-specific. Reuse these for any future toy game rather than inventing new per-game equivalents.

### Read a Story (`src/components/Story/Story.tsx`)
A fourth top-level practice mode, entered via a `.mode-card` on Home or the TopNav's "读故事" tab (`GO_TO_SCREEN "story"`) — **deliberately independent of the Quiz/Result/`QuestionGroup` pipeline**, same reasoning as Tingxie: it's not a graded activity, just a reading/read-aloud tool, so it doesn't touch BP/achievements/Today's Mission at all.

- **Local state, single file, no reducer**: everything (`view: "picker" | "reading"`, `lessonId`, `segmentIndex`) is plain `useState` inside `Story()` — no `TingxieProvider`-style local Context/reducer, since there's no queue mechanic or multiple activities to coordinate here, just two numbers. `StoryReader` (the reading view) is a **separate top-level function**, not nested inside `Story()`'s body — nesting it would give React a new component identity every render and force a full remount on every parent re-render, wiping its `segmentSpeaking` toggle state each time (same reasoning as `Quiz.tsx`'s `PassageBox` being defined outside `Quiz()`).
- **Lesson picker** (`view: "picker"`): a `.lesson-grid` of `LESSON_COUNT` (`data/questions.ts`) lesson buttons, same classes as Tingxie's `LessonSelect.tsx` and Practice's lesson picker (`.lesson-btn`/`.lesson-btn-num`). A `STORY_LESSONS[id].placeholder` lesson (see `data/stories.ts`) shows a "敬请期待 Coming soon" badge (reusing `.lesson-btn-count`) but is still clickable — it opens straight into its one-page "coming soon" stub rather than being disabled, so the picker isn't mostly-greyed-out while only Lesson 1 has real content.
- **Reading view** (`view: "reading"`): pages through `lesson.segments[segmentIndex]` one page at a time. Every page groups one or more of the story's original paragraphs so it has **at least 3 sentences** (a lone short paragraph gets merged onto a neighboring page rather than left as its own sparse page) — paragraph boundaries are still preserved for rendering (`StorySegment.paragraphs: string[][]`, each inner array one paragraph, each rendered as its own `<p className="story-paragraph">`), so a page can show more than one paragraph without losing the story's original line breaks. `data/stories.ts`'s `segmentSentences(segment)` flattens a page's paragraphs into one sentence list where a flat list is what's actually needed (the segment-level dictation button, page-length checks).
- **Page-turn navigation**: a curled-paper-corner button in the page's bottom-right (`.story-page-curl-next`) flips forward, bottom-left (`.story-page-curl-prev`, the same shape mirrored via `scaleX(-1)`) flips back — no plain "Prev"/"Next" text buttons. Each corner only renders when that direction actually goes somewhere (first/last page have no wraparound). Clicking one runs `StoryReader`'s `flipTo(direction)`, a two-phase animation sequenced entirely in JS (`FLIP_MS` = 260ms per phase): phase "out" rotates the current page away in 3D (`.story-page-flip-{next,prev}-out`, `transform-origin` on the corresponding edge) via a `setTimeout` matching `FLIP_MS`; once that fires, `segmentIndex` actually advances and phase "in" rotates the new page into place from the opposite extreme (`.story-page-flip-{next,prev}-in`) via a second matching `setTimeout`. One content slot plays both halves in sequence rather than rendering two full pages layered on top of each other, which keeps the state machine simple (`flip: { direction, phase } | null`) at the cost of a strict "can't start a new flip until the current one finishes" (`if (flip) return;` guard, also `disabled` on both curl buttons while `flip !== null`). The `.story-page-flipper` wrapper supplies `perspective` for the 3D effect; the animations are gated behind `@media (prefers-reduced-motion: no-preference)` so a reduced-motion student just gets an instant page swap at the same JS-timer cadence, no visual rotation.
- **Two independent read-aloud affordances per page**, both via `lib/speech.ts`'s `speakText()`/`stopSpeaking()`:
  - A page-level "🔊 朗读本段 / ⏹ 停止" toggle button (`.dictation-btn`/`.dictation-btn-active`, identical pattern to Quiz.tsx's `PassageBox`) that reads every sentence on the page concatenated together, and can be stopped mid-read by clicking it again.
  - Each individual sentence is its own tappable `<button className="story-sentence">` (full button-chrome reset, `display: inline` so sentences still flow together as one paragraph) — clicking one reads *only* that sentence via a plain one-shot `speakText(sentence)` call, no toggle state of its own.
  Clicking a sentence while the page-level reading is in progress interrupts it (`speakText()` always cancels any prior utterance first) and immediately resets the page-level button back to its "🔊" state (an explicit `setSegmentSpeaking(false)` right before the call, not just relying on the async `onDone` callback, so the button's visual state doesn't lag behind the click). `Story.tsx`'s top-level `useEffect` also calls `stopSpeaking()` on every lesson/page/view change and on unmount, same lingering-speech fix as Quiz.tsx/Tingxie's shell-level guard.
- **Sentence data is hand-authored, not runtime-split** — see the `data/stories.ts` bullet above for why (Chinese dialogue punctuation doesn't split cleanly with a generic 。！？ regex once quotes are involved).

### Tingxie / 听写 dictation practice (`src/components/Tingxie/`)
A third top-level practice mode, entered via a `.mode-card` on Home (`GO_TO_SCREEN "tingxie"`) — **deliberately independent of the Quiz/Result/`QuestionGroup` pipeline**. It was ported from a separate standalone app (functionality only, not its Tailwind styling or its points-ledger system) and reuses this app's BP/pet economy instead of a second reward system.

- **Local state, not global**: `Tingxie.tsx` mounts its own `TingxieProvider` (`tingxieState.tsx` — a `useReducer` + two Contexts, `useTingxieState()`/`useTingxieDispatch()`, same shape as `AppStateContext.tsx` but scoped entirely to this subtree). `AppStateContext`'s `Screen` union only knows about a single `"tingxie"` entry point; everything that happens after that (lesson selection, which of the 3 activities is active, flip/queue progress) lives in this local reducer and is **not persisted** — leaving the mode resets it, by design (no localStorage key for it). The one deliberate exception is a single timestamp in `state/tingxieProgress.ts`, marking that *some* activity completed today — just enough for Home's Today's Mission to see it after the fact (see below), without persisting anything about *which* lesson/activity.
- **Stops its own read-aloud on navigation**: `Tingxie.tsx`'s shell calls `speech.ts`'s `stopSpeaking()` whenever `view`/`subTab`/`activeContent` changes or the component unmounts — the same lingering-speech fix as Quiz.tsx's dictation button, applied once at the shell level since every one of Tingxie's `speakText()` call sites (vocab/sentence/apply/practice "🔊 朗读 Listen" buttons) benefits from it. The shell-level fix only covers *navigation*, not an in-place flip — `Apply.tsx` additionally calls `stopSpeaking()` itself (a `useEffect` on `state.applyFlipped`) so a reading started from the front's Listen button doesn't keep playing after the student flips to the answer; `Practice.tsx`'s sentence phase doesn't need the same guard since its front-side Listen button (see below) and back-side one both read the same text.
- **Data loading**: the app's first and only runtime `fetch()` — lesson content is fetched on demand from static JSON in `public/tingxie-lessons/<id>.json` (+ `index.json`) rather than bundled as TS/JSON imports, specifically so new lessons can be dropped in without a rebuild (`src/data/tingxie.ts`'s `fetchTingxieLessonIndex()`/`fetchTingxieLesson()`, each with a small module-level `Map` cache). Every other screen/data file in this app is bundled at build time; this is the one deliberate exception.
- **Three activities per lesson**, switched via tabs in `Tingxie.tsx`'s top bar once a lesson (or custom review) is active:
  - **Learn** (`Learn.tsx`, `subTab: "vocab" | "sentence"`): 学词语 is a 3D flip-card carousel (`TingxieFlipCard.tsx` — a shared `perspective`/`backface-visibility`/`rotateY` shell reused by Apply/Practice too) over `lesson.vocab`; 学默写 is a sentence-reordering game — word chips (`lib/tingxieSentenceWords()` strips punctuation tokens out of `sentence.segments`) are placed into a tray, and placing them in ascending index order (vs. the shuffled `chipOrder`) is what "correct" means, so the reducer never has to store or re-derive the actual word sequence.
  - **Apply** (`Apply.tsx`, 词语应用): one flip-card per vocab word that has `sentenceBank` entries — front shows a blanked example sentence (`tingxieBlankWord()`, literal substring replace) + English gloss, back reveals the word.
  - **Practice** (`Practice.tsx`, 听写练习): two phases in one queue — vocab (auto-speaks the word via `speakText()` when each card appears, not on click) then, once that queue empties, sentences (no auto-speak, but the front face has its own manual "🔊 朗读 Listen" button reading the target sentence, so the student can attempt the dictation before flipping — same text is also readable from the back) — the reducer swaps in the sentence-phase queue internally, so the component only dispatches `PRACTICE_START` once per visit.
  - Apply/Practice share a **front-shrink/back-requeue queue mechanic**: a correct self-grade drops the current item off the front; a miss moves it to the back so it resurfaces later the same pass — not persisted between visits. A miss (only) also calls `state/todaySummary.ts`'s `recordTingxieWrong()` — see that bullet in the History/achievements/stats section for what this feeds (the Home "今日学习总结 Today's Session Summary" PDF) and why only misses are recorded, not every item practiced.
- **Custom review** (`TingxiePicker.tsx`, 自由复习): multi-select checkboxes over the lesson index; on start, fetches every selected lesson and pools them (`pooledTingxieReview()` — samples up to `TINGXIE_REVIEW_VOCAB_COUNT`/`TINGXIE_REVIEW_SENTENCE_COUNT` items, merges every selected lesson's `sentenceBank` in full, uncapped) into one synthetic `TingxieActiveContent` fed straight into Apply or Practice. The Learn tab and its BP award are hidden/skipped entirely in this mode — there's no per-lesson "visit" for pooled content.
- **BP**: `TINGXIE_BP_AWARD` in `data/pet.ts` (`VOCAB_LEARN`/`SENTENCE_LEARN`: 10, `APPLY`: 10, `PRACTICE`: 20 — carried over from the source app's point values). Each award fires at most once per mount, guarded by a plain `useRef` in the awarding component (not reducer state) — since Learn/Apply/Practice remount fresh every time the student navigates back into them, replaying an activity re-earns BP, matching the source app. Each of these 4 award sites also calls `state/tingxieProgress.ts`'s `recordTingxieActivityCompleted()` and `state/achievements.ts`'s `checkAndAwardMissionBonus()` right alongside — this is what feeds Home's "听写练习 Dictation Lesson" Today's Mission (see `TodayMission` in the Screens section) and its bonus-BP payout.
- **Sound**: flips/tabs/nav need no explicit call (they're real `<button>`s or `.tingxie-flip-card`, both matched by `App.tsx`'s global click listener, which now also plays a click sound of its own — see Sound below). `Sound.ding()`/`Sound.miss()` for correct/incorrect self-grades and sentence-order checks; `Sound.gift()` for BP-award-on-completion.
- **`TingxieFlipCard`'s back face contains real `<button>`s** (TTS, self-grade), so its outer clickable region is a `<div role="button" tabIndex={0}>`, not a `<button>` — nesting a button inside a button is invalid HTML (the same constraint `PetHeroCard` used to have). Its click handler calls `e.stopPropagation()` where needed so a click on an inner button doesn't also toggle the flip.
- **Icon decoration**: `sentence.icon` (a Lucide icon name from the source data) is mapped to an emoji via `tingxieIconEmoji()`'s lookup table in `data/tingxie.ts` (with a `✨` fallback for unmapped names); `sentence.color` (a Tailwind class) is kept on the type for JSON fidelity but never read.

### Pet / BP layer (`src/data/pet.ts` + `src/state/PetContext.tsx`)
`PetProvider` holds `PetState` in `useState`, persisted to `localStorage` under `PET_KEY` (`hanyuPracticePet_v1`) on every change; `usePet()` exposes `{ pet, awardBP, buyItem, giveItem, consumeItem, applyPlayReward, renameOwl, recordQuestionsCompleted }`.

- **Mood is derived, never stored as a live value**: `pet.moodAtCheckpoint` + `pet.lastFedAt` is a fixed pair, and `computeCurrentMood()` decays from that pair fresh on every call (not a decay tick) — this is what makes time-based neglect work without a server, and avoids compounding rounding error from repeatedly decaying an already-decayed number. `growth` is monotonic and completely decoupled from mood/decay.
- **BP** is awarded via `awardBP()`, called from `Quiz.tsx` for MCQ/Fill-in (immediately on grading) and for Long-Answer/Writing-Constrained (from the self-check "✓" handler, guarded by a `bpAwarded` flag on the result item so re-toggling doesn't double-pay).
- **Bag/inventory**: `PetState.inventory` is a `Record<shopItemId, quantity>`. `buyItem()` deducts BP and adds to inventory; it does *not* touch growth/mood. `giveItem()` (food, and the old instant-give path) applies a `ShopItem`'s growth/mood effect *and* decrements inventory in one step — called from `Bag.tsx` once that item's throw animation lands, never directly from the Shop. Toys instead split those two steps across the Play flow (see the Toy minigames section above): `consumeItem(item)` only decrements inventory (called the moment a toy's minigame starts), and `applyPlayReward(item, moodReward)` only applies growth + an explicit mood amount (called once the minigame reports a score) — both share `giveItem()`'s internal `applyGrowthAndMood()` helper so the age/mood math itself isn't duplicated. None of `giveItem()`/`consumeItem()`/`applyPlayReward()` log an achievement for feeding, playing, or evolving — pet-interaction events are deliberately not tracked at all (only learning activity is, see `RecentAchievements` above), so a feed or play that crosses into a new `PetStage` is reflected only in the pet's own state, never in the achievement log. `giveItem()`/`applyPlayReward()` both **return `{ agedUp, age }`** (`agedUp` true whenever that call crossed a 100-growth age-year boundary — see the Age note above; always true on a genuine stage evolution too, since every `PetStage.minAgeYears` is itself a specific age) so the caller knows to play `Sound.levelUp()` + show an age-up message instead of the routine `Sound.gift()`.
- **`recordQuestionsCompleted(n)`**: pure increment of `PetState.questionsLifetime`, called once per session from `Result.tsx` — kept arithmetic-only (no achievement logic inside it) so the milestone check can be computed from the pre-call value without reading a stale/batched value back out of context.
- **Naming**: `PetState.name` (default `""`, shown as a placeholder prompt until set), edited via `renameOwl()` (trims, caps at 12 chars).
- Cross-device sync (accounts, Supabase — `@supabase/supabase-js` is already a dependency) is an intentionally separate, not-yet-built later phase; `PetState`'s flat, serializable shape is designed so a future sync layer can push/pull it without a local data-model rewrite.

### Owl art (`OwlArt.tsx` + `pet.ts`)
One static PNG per stage × mood bucket lives in `public/owl/` (`owl-<stage>-<mood>.png`, e.g. `owl-baby-happy.png` — 6 stages × 4 moods = 24 assets, `owlSpritePath()`). A stage/mood combo can instead have a hand-animated **MP4** (H.264 + AAC, sound muxed into the video's own audio track — not a separate audio file) that `OwlArt` prefers over the PNG when present, driven by the `ANIMATED_OWL_VARIANTS` allowlist in `pet.ts` (currently `"egg-very_happy"`, `"baby-very_happy"`, `"egg-sad"`, and `"egg-neutral"`, with more of the 24 combos to follow — note `"egg-sad"`/`"egg-neutral"` have no PNG fallback anymore, their source PNGs were deleted when the video replaced them, unlike the first two which still keep theirs). The `<video>` has no `loop` (plays once, holds the last frame) and is only unmuted when `OwlArt`'s `playSound` prop is set — on the Home hero card, the Owl screen, and the Bag/"Feed" screen, i.e. everywhere the pet is a primary focus of the screen. `OwlArt` forwards a ref to its root element so `Bag.tsx`'s throw animation can target the owl's on-screen position.

### Sound (`src/lib/sound.ts`)
Only `gift()` (rising triangle-wave glissando, giving an item to the owl in the Bag when it *doesn't* cross an age-year boundary, and reused for Tingxie's BP-award-on-completion) is still a pure synthesized Web Audio waveform — every other effect plays a real MP3 file: `click()` (any button press, wired up globally in `App.tsx` via a document-level click listener on `button, .option-label, .tingxie-flip-card`), `ding()`/`miss()` (a correct/wrong answer — Quiz MCQ/Fill-in/self-check, Tingxie self-grade/sentence-order; `miss()` stays silent on a skipped/unanswered Quiz question, only a genuine wrong pick plays it), `applause()`/`encourage()` (a quiz or Tingxie session scoring ≥90% / <90%), `purchase()` (a Shop buy), `levelUp()` (a feed crosses a 100-growth age-year boundary, `giveItem()`'s returned `agedUp` — this includes but isn't limited to stage evolutions, see the Age note above and `PetContext.tsx`'s `giveItem()`), `enterShop()` (opening the Shop screen, from both its entry points — `Owl.tsx`'s Shop button and Bag.tsx's empty-bag "Visit Shop" button), and `bagOpen()` (opening the Bag/Feed screen from `Owl.tsx`'s Feed button). These specific-action sounds are layered *alongside* the generic `click()` sound the global listener already fires for the same button press (see `Shop.tsx`'s `handleBuy()` for the original precedent — `buyItem()` + `Sound.purchase()` right next to the click listener's own `Sound.click()`), not a replacement for it.

**Background music** (`background.mp3`) is structurally different from every other sound above: it's a single `HTMLAudioElement` held in a module-level variable (`bgMusic` in `sound.ts`), not a fresh fire-and-forget element per call like `playFile()` — this is what lets it survive screen navigation (React unmounting/remounting components never touches a module-level reference) and keeps it from ever restarting from the beginning. `Sound.startBackgroundMusic()` is idempotent (creates the element once, sets `loop = true`, and only calls `.play()` if it's currently paused) and is called from `App.tsx`'s existing global click listener on *every* click, not just button clicks — this is the standard workaround for browsers only allowing unmuted audio to autoplay after a genuine user gesture: the loop can't start on mount, so it starts on the app's first click, and every click after that is a cheap no-op once it's actually playing (or a retry if that first gesture somehow didn't count). `App.tsx` also has a separate `document.visibilitychange` listener (independent of the click listener) that calls `Sound.pauseBackgroundMusic()` when the tab is hidden and `Sound.startBackgroundMusic()` when it becomes visible again — resuming an `<audio>` element that already played once doesn't need a fresh user gesture, so this doesn't hit the autoplay restriction.

**MP3 files live in `public/sounds/`** (`button.mp3`, `correct.mp3`, `wrong-answer.mp3`, `good-result.mp3`, `need-improvement.mp3`, `purchase.mp3`, `level-up.mp3`, `enter-shop.mp3`, `bag-open.mp3` — the exact filenames `sound.ts`'s `SOUND_FILES` map expects). Drop a replacement in with the same filename and it's picked up automatically, no code change needed. Playback is a plain `new Audio(path).play()` per call (not the Web Audio API graph used by `gift()`) — a fresh element each time so overlapping/staggered triggers (e.g. multiple correct dings in one quiz-group submit, scheduled via `ding()`'s `delay` param) don't cut each other off. Every URL has a `?v=<timestamp computed once at module load>` cache-buster appended — without it, a browser that already cached a stale response for a filename (the pre-launch 404, or a since-replaced MP3) keeps serving that stale response indefinitely since the URL never otherwise changes; this was a real bug (a replaced `purchase.mp3` kept playing the old file) before the cache-buster was added. A missing/404 file fails silently (caught, never blocks interaction) — the app runs fine before the files are actually dropped in, just silently.

### History, achievements, and stats (`src/state/history.ts`, `src/state/achievements.ts`, `src/state/tingxieProgress.ts`, `src/state/todaySummary.ts`, `src/lib/stats.ts`)
- `history.ts` persists the last 50 session summaries to `localStorage` under `HISTORY_KEY` (`hanyuPracticeHistory_v2`; bump this key if the stored shape changes, to avoid crashing on old data). Each `HistoryEntry` has an `id` (assigned on save; `loadHistory()` lazily backfills `id` onto any pre-existing entries that predate the delete feature) so `Home.tsx` can delete individual rows or clear all of them. Lifetime, but summary-only — no question-level detail (that's `todaySummary.ts`'s job, see below).
- `todaySummary.ts` persists `localStorage` under `TODAY_SUMMARY_KEY` (`hanyuPracticeTodaySummary_v1`) — the full-detail counterpart to `history.ts`'s lifetime summary, but bounded to **today only**: `loadStore()` discards (and re-persists empty) anything whose stored `dateKey` isn't today's, so this never grows into a second unbounded copy of practice history. Two independent lists: `practiceSessions` (`recordTodayPracticeSession()`, called from `Result.tsx` for every finished quiz session regardless of `mode` — full `QuestionGroup[]`/`GroupResult[]` detail, capped at 20/day) and `tingxieWrong` (`recordTingxieWrong()`, called from Tingxie's `Apply.tsx`/`Practice.tsx` `missed()` handlers **only** — i.e. only items the student explicitly self-graded "✗ 答错了/记错了", not every item practiced; deduped by `kind`+`answer` so the front-shrink/back-requeue queue mechanic re-missing the same word doesn't create repeat rows, capped at 100/day). Feeds `lib/exportPdf.ts`'s `exportTodaySummaryToPdf()` (see the Home bullet above). Deliberately not wired to `history.ts`'s delete/clear-all — deleting a `RecentAchievements` row does not remove that session from today's PDF; this store resets naturally at the next calendar day regardless, so the inconsistency window is at most one day.
- `achievements.ts` persists up to the 30 most recent `Achievement`s to `localStorage` under `ACHIEVEMENTS_KEY` (`hanyuPracticeAchievements_v1`), written via `logAchievement()`. Only learning-related types exist (`"missionComplete" | "questionsMilestone"` — pet feeding/evolving is intentionally never logged, see the `giveItem()` note above). Dedup rules differ by type: `"missionComplete"` recurs at most once per calendar day (`dateKey`-scoped); `"questionsMilestone"` can only genuinely be earned once ever (`questionsLifetime` is monotonic), so it's deduped by milestone number forever, not just for the day. Also exports `hasLoggedToday(type)` (checked *before* `logAchievement()` by callers that need to know whether the entry they're about to write is genuinely new, not a dedup no-op — `logAchievement()` itself is fire-and-forget void) and `checkAndAwardMissionBonus(hist, awardBP)`, the single entry point for the "all 3 Today's Missions done" check + `MISSION_COMPLETE_BONUS_BP` payout, called from both `Result.tsx` and Tingxie's four completion sites.
- `tingxieProgress.ts` persists exactly one thing under `TINGXIE_PROGRESS_KEY` (`hanyuPracticeTingxieProgress_v1`): the timestamp of the last completed Tingxie activity (`recordTingxieActivityCompleted()`/`getTingxieLastCompletedAt()`) — the sole exception to Tingxie's "nothing persists" rule (see the Tingxie section), needed so `TodayMission` can see it after Tingxie unmounts. Deliberately has zero imports from `achievements.ts`/`history.ts` even though its callers always pair it with a `checkAndAwardMissionBonus()` call — `stats.ts` already imports this file, and `achievements.ts` imports `stats.ts`, so importing either back would create a 3-file cycle; callers call both functions directly instead.
- `stats.ts` is the shared home for date-bucketing/derived-stat logic used across the dashboard: `dateKey()` (local-calendar-day key, DST-safe — not raw ms division), `getTodayStats()` (used by `PetHeroCard`'s subgreeting), `formatRelativeTime()`, plus the Today's Mission helpers `READING_MISSION_CATEGORIES`, `isLessonMissionComplete()`, `getReadingMissionCount()`, `isTingxieMissionComplete()` (reads `tingxieProgress.ts`), `areAllMissionsComplete()` (all 3).

### Styling (`src/styles/styles.css`)
Single global stylesheet, currently a **claymorphism** design system (candy pastel palette, puffy double-shadow cards, pill-shaped bars/badges/buttons, squish hover/press interactions) — this replaced an earlier "scholar's-study" terracotta-and-serif look, itself previewed on just the Home dashboard before being promoted app-wide once approved. Light mode only — there used to be a `@media (prefers-color-scheme: dark)` override block on the CSS custom properties, but dark mode was deliberately removed; don't re-add a dark-mode media query without being asked. No CSS modules/CSS-in-JS — components just reference global class names, and no external fonts/CDNs (the app must keep working fully offline).

- **Tokens** (`:root`): `--primary`/`--primary-hi`/`--primary-dark` (coral), `--gold`/`--gold-hi`/`--gold-deep` (BP/streak accent), `--correct`/`--incorrect`, `--ink`/`--ink-rgb`/`--ink-soft` (text), `--card-bg`/`--card-hi`/`--border`/`--hi-edge`, and the shadow trio `--shadow-1`/`--shadow-2`/`--shadow-press` — each a *pair* of shadows (soft outer lift + inset highlight, or double-inset when pressed) rather than a single flat shadow, which is what gives the "puffy clay" look to every class that references them. Because so many shared classes (`.dash-card`, `.mode-card`, buttons, badges, bars, and each screen's own card classes) already consumed these tokens rather than hardcoding colors, retheming the whole app was mostly a token swap plus per-class border-radius/border tweaks, not a rewrite — the same mechanism the old dark-mode override used to use.
- **`.screen`** (the common wrapper class every top-level screen renders, e.g. `<div className="screen owl-screen">`) carries the shared pastel gradient panel background + big border-radius + padding that every screen sits on. **`.home`** overrides that panel back to `background: none; border-radius: 0` (source order lets `.home`'s rule win over `.screen`'s) — Home deliberately has no single outer "everything card"; each dashboard section (`PetHeroCard`, `TodayMission`, Continue Learning, `RecentAchievements`) is its own `.dash-card` floating directly on the page background instead, not nested inside a bigger enclosing card. `.home` also still gets an extra flourish on top: two blurred, slowly-drifting gradient blobs (`::before`/`::after`, `isolation: isolate` + `overflow: hidden` + negative `z-index` so they sit behind the dashboard cards) — deliberately not spread to every screen, so the app has exactly one "boldest" ambient-motion moment rather than a dozen competing ones.
- **Badges** (`.marks-badge`, `.quiz-bp-badge`, `.pet-status-bp`, `.pet-hero-stage-badge`, `.stat-tile-badge`) used to be a rotated "seal stamp" (carved bevel, `rotate(-3deg)`); they're now unrotated puffy pills (`border-radius: 999px`, `var(--shadow-1)`, `scale(1.06)` on hover) matching the rounder shape language everywhere else.
- **Bars** (`.growth-bar`/`.mood-bar`) are pill-shaped (`border-radius: 999px`) with a `::after` shine sweep (`clay-bar-shine` keyframes, ~3.4s, respects `prefers-reduced-motion`) so they read as gently alive rather than static.
- **Squish interactions**: most interactive cards/buttons (`.mode-card`, `.mission-row`, `.stat-tile`, `.primary-btn`/`.secondary-btn`, `.lesson-btn`, `.shop-item-card`, `.bag-item-card`, `.tingxie-tab`/`.tingxie-subtab`/`.tingxie-picker-row`/`.tingxie-chip`, etc.) lift + scale up slightly on hover and scale *down* on `:active` (rather than the old flat `translateY`), for a tactile "press" feel.

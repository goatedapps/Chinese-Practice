## What this is

A Vite + React + TypeScript web app for practicing Chinese-language exam questions (Primary school Chinese / Higher Chinese, Singapore-style "语文应用": cloze, error correction, reading comprehension, dialogue completion, hanyu pinyin, etc.), with a Tamagotchi-style gamification layer (earn BP for correct answers, hatch and grow a pet owl, feed/play with it via a shop + bag). The app needs no backend and works fully offline once built/served — every visitor lands on a login page first (see the Auth / cross-device sync section below), but can click through as a guest with one tap and never see it again on that device; login itself is otherwise optional, and unconfigured (no Supabase project wired up), sign-in/sign-up just show a "not configured" error while guest mode still works with zero setup.

## Running / testing

Standard Vite/npm project — no test suite (verify changes by running the dev server and clicking through the flow manually):

- `npm install` — install dependencies (React 19, `@supabase/supabase-js` backs optional login/cross-device sync, see the Auth / cross-device sync section below; `yaml` parses the runtime-fetched content files under `public/content/`, see the Content files section below; `tsx` is a dev-only dependency for running the one-off/maintenance scripts under `scripts/`).
- Login/sync need a Supabase project: run `supabase/schema.sql` once in that project's SQL editor, then copy `.env.example` to `.env.local` and fill in `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`. Both `npm run dev` and `npm run build` work fine with no `.env.local` at all — `src/lib/supabase.ts` exports `null` instead of throwing, and the app is fully local/offline exactly as before.
- `npm run dev` — start the Vite dev server.
- `npm run build` — `tsc -b && vite build`; always run this (or at least `npx tsc -b`) after non-trivial changes, since there's no test suite to catch regressions otherwise.
- `npm run lint` — `oxlint`.
- `npm run preview` — serve the production build locally.
- `npm run build-content-index` — regenerates the three `index.yaml` files under `public/content/p5/` from whatever's actually on disk (pass a level id, e.g. `npm run build-content-index -- p2`, to target a different level — it defaults to `p5` with no argument). **Run this after hand-editing any content file** (a question/Tingxie/story file) — the index isn't recomputed automatically, so a stale index would otherwise silently keep serving pre-edit lesson counts/category availability to the Practice/Home pickers. See the Content files section below.

## Architecture

### Content files (`public/content/<level>/`)
All practice content — questions, Tingxie lessons, Read a Story passages — lives as **human-editable YAML/Markdown files under `public/content/<level>/`**, not as TS/JSON literals, and is fetched at runtime (not bundled into the JS build). `<level>` is currently always `p5` (Primary 5) — see the Levels note below for how this is meant to grow. This replaced an earlier version where `questions.ts`/`stories.ts` were large hand-edited TS array literals bundled at build time (`stories.ts` alone was 655 lines, `questions.ts` 5926) and only Tingxie fetched its JSON at runtime; the migration generalized Tingxie's pattern to all three and moved authoring out of TS syntax entirely. If you're editing practice content, **edit the files under `public/content/p5/`**, not `src/data/*.ts` — the `src/data/` files are now thin loaders (fetch + cache + a couple of derived helpers), not the data itself.

- **`public/content/p5/meta.yaml`** — level-wide metadata: `label` (display name) and `lessonCount` (drives both the Practice screen's lesson grid and the Read a Story picker's lesson-button count — bump this for a new lesson number, no other file needs to change).
- **`public/content/p5/questions/`** — one YAML file per **category** (`pinyin.yaml`, `vocab.yaml`, `cloze.yaml`, ... one per `CATEGORIES` key in `data/questions.ts`), each a plain YAML list of every group in that category (both standalone single-question groups and passage-bearing ones — there's no further per-paper split). A **group** is either a standalone question (`passage: null`) or a passage plus every question that shares it — always presented and graded together, never split apart. The on-disk shape is deliberately leaner than the in-memory `QuestionGroup`/`Question` shape (`data/types.ts`) — every field that's redundant or constant-per-category is dropped from the YAML and synthesized back by `data/questions.ts`'s `parseQuestionCategoryYaml()` when a category is loaded (see below for exactly which fields and why); nothing downstream of that function (`Quiz.tsx`, `grading.ts`, `exportPdf.ts`, `mcqShuffle.ts`, `typeSession.ts`, ...) ever sees the on-disk shape, so authoring convenience and runtime shape can evolve independently. Two shapes exist, matching a real structural split in the data:
  - **The 6 "flat" categories — `pinyin`, `vocab`, `phrase`, `usage`, `conjunction`, `sentence`** (`FLAT_CATEGORIES` in `data/questions.ts`) — every group in these is (and was verified to always be) `subject: Chinese`, `format: MCQ`, `marks: 2`, `passage: null`, exactly one question. So a group is just:
    ```yaml
    - questionID: CH-Q3          # was groupId
      lessonIds: [11]
      question: 大家非常痛 ___ 明华伤害小动物的行为。
      options: [很, 恨, 狠, 银]   # was options: [{key, text}], no keys any more
      correct: 恨                 # was correctKey: "2" -- matches an option's text, not its position
    ```
    `subject`/`category`/`marks`/`format` aren't authored at all (implied), and `correct` identifies the right option **by its text**, not a 1-based key/index — deliberately, so reordering/inserting/deleting an option by hand can never silently desync it from a stale index the way a position-based reference would. `data/questions.ts`'s `expandFlatRecord()` synthesizes `groupId = questionID`, `subject: "Chinese"`, `marks: 2`, `format: "MCQ"`, `passage: null`, and rebuilds `options` as `{key, text}[]` with keys `"1".."N"` in authored order, resolving `correctKey` by matching `correct` against an option's `text` (throws at load time if nothing matches — a fast way to catch a typo).
  - **The 5 "passage" categories — `cloze`, `comprehension`, `dialogue`, `errorcorrect`, `practical`** — still genuinely need a shared id per passage and can have several questions of different formats/marks per group, so they keep `groupId`/`passage`/multi-question `questions[]`, but every field that's constant *within a given category* becomes optional there, defaulting back in on load (`expandGroup()`):
    - `category` is never authored anywhere any more (all 11 files) — it's always just the filename, both in `parseQuestionCategoryYaml(category, text)`'s `category` argument and in `scripts/build-content-index.ts`'s per-file loop.
    - `subject` is omitted and defaults per-category (`CATEGORY_DEFAULT_SUBJECT`: `dialogue`/`practical` → `"Chinese"`, `errorcorrect` → `"Higher Chinese"`) — except `cloze`/`comprehension`, which genuinely mix Chinese and Higher Chinese groups within one file, so `subject` stays a required per-group field there (per the earlier ask to keep it for comprehension — it turned out cloze needed the same treatment for the same reason).
    - `lessonIds` is optional on a group (`RawGroup.lessonIds?`, defaults to `[]` in `expandGroup()`) and omitted entirely in `cloze.yaml`/`comprehension.yaml` — both are `lessonMode: false`, so `lessonIds`/the derived `lessonEligible` are never read for these two categories (Practice.tsx's lesson filter only ever applies to `VOCABULARY_CATEGORY_KEYS`, see the `lessonIds` bullet below) and every group in both files had `lessonIds: []` anyway. `dialogue`/`errorcorrect`/`practical` still author `lessonIds: []` per group even though it's equally unused for them today — left alone since only cloze/comprehension were asked to be tidied up; there'd be no behavior difference in dropping it from those three too.
    - A passage's `source` field (`Passage.source?: string`, shown in `Quiz.tsx`'s `PassageBox` and the PDF export when present) is likewise dropped entirely from `cloze.yaml`/`comprehension.yaml` — deemed not worth showing for these two categories. No code change was needed: `passage.source` was already optional and its display already conditional (`{passage.source && ...}`), so simply omitting the field is enough. Still authored (and shown) in `dialogue`/`errorcorrect`/`practical`.
    - Per-question `format` is omitted and defaults per-category (`CATEGORY_DEFAULT_FORMAT`: `dialogue` → `"MCQ"`, `errorcorrect` → `"Fill-in"`) — `cloze`/`comprehension`/`practical` genuinely mix formats within a file (e.g. `comprehension` mixes Fill-in/Long-Answer/MCQ, `practical` mixes MCQ/Writing-Constrained), so `format` stays required there.
    - Per-question `marks` is omitted and defaults to `2` **everywhere**, category-independent — every question across the whole bank is `marks: 2` except a handful of `comprehension`/`practical` Long-Answer/Writing-Constrained items (`marks: 3/4/5`), which just write `marks: N` explicitly.
    - An MCQ question's own `options`/`correct` follow the same key-free, text-based convention as the flat categories above (`options: [...]` + `correct: <matching text>`). A group's shared `optionBank` (dialogue) is likewise now a plain `optionBank: [text, ...]` list (no `key` field) — a bank-referencing question's `correct` matches straight against the bank's text, the same as if it had its own `options`. `Quiz.tsx`'s "词语库 Word Bank" numbering (`${opt.key}. ${opt.text}`) is unaffected since the synthesized `"1".."N"` keys exactly match the old authored ones (verified — see the migration bullet below).
    - Fill-in (`accepted`/`displayAnswer`) and Long-Answer/Writing-Constrained (`displayAnswer`, optional `context`/`notes`) are unchanged — those were already concise and weren't part of this simplification.
    
    Example (`dialogue.yaml`, all defaults applying so `subject`/`format`/`marks` never appear):
    ```yaml
    - groupId: CH-G3
      lessonIds: []
      passage: { title: ..., source: ..., text: | ... }
      optionBank: [只要赢了这场游戏, 应该让眼睛好好休息, ...]
      questions:
        - text: 小强：___？（回应妈妈问他为什么还在玩电脑游戏）
          correct: 我可以再玩半个小时吗
    ```
  - **`data/questions.ts`'s `parseQuestionCategoryYaml(category, yamlText)`** is the one pure function (no fetch, no cache) that expands either on-disk shape into `QuestionGroup[]` — shared by the runtime loader (`fetchQuestionCategory()`, which just fetches+caches then calls it) and `scripts/build-content-index.ts` (which reads the file itself, since Node has no `public/`-relative `fetch()`), so the index-rebuild script validates content exactly the same way the app does (a `correct` that doesn't match any option throws in both places, immediately, rather than silently breaking a quiz later).
  - To add a new group: append it to the right category file in the shape above, then run `npm run build-content-index` (see below) so the index picks it up. To add a new question type: add a key to `CATEGORIES` in `data/questions.ts` and create its `<category>.yaml` file — a category with real per-group `subject`/`format` variation should use the passage-group shape (with `groupId`) even for single-question groups; the flat shape is only for the 6 categories above.
  - **The rest of the app is completely unaffected by this file-format simplification** — `data/types.ts`'s `QuestionGroup`/`Question`/`MCQOption` (the in-memory shape) didn't change at all, so `Quiz.tsx`, `grading.ts`, `exportPdf.ts`, `mcqShuffle.ts`, `lib/typeSession.ts`, `Practice.tsx`, etc. needed zero changes — only `parseQuestionCategoryYaml()` (and its one caller, `fetchQuestionCategory()`) knows the on-disk shape exists.
  - **Migrating existing content to this shape**: done once via `scripts/migrate-question-schema.ts` (`npx tsx scripts/migrate-question-schema.ts <level>`) for both `p5` and `p2` — reads the old groupId/subject/category/marks/format/keyed-options shape and rewrites every category file in place. Verified lossless against the pre-migration content (all 849 questions across both levels — every question's text/marks/format/options/correct-answer/passage/optionBank/context/notes byte-for-byte round-tripped) before being treated as done. Kept for reference (same convention as `migrate-content.ts` below) in case a future level still has old-shape content to convert; not meant to be re-run against already-migrated files.
  - **Two other fields that used to be authored are dropped from the YAML and computed by the loader instead**, because they were fully redundant: `qNo` (a per-question id, e.g. `"Q1"`) is synthesized as `` `${groupId}-${index}` `` — it was never parsed back out of the data by any code, only used within a single quiz session to correlate an answer/result to its question (`Quiz.tsx`'s answer map/radio names, `grading.ts`, `exportPdf.ts`). `lessonEligible` is synthesized as `lessonIds.length > 0` — verified true for every one of the 357 groups that existed at migration time, so it never needs to be authored, but it's still present on the in-memory `QuestionGroup` object so existing call sites (e.g. `Practice.tsx`) don't need to change. Two other exam-provenance fields (`paper`, `section`) were dropped entirely (not computed, not kept) since neither was read anywhere in the app.
  - **`questions/index.yaml`** — a generated, lightweight index (`groupId`, `subject`, `category`, `lessonIds`, `questionCount` per group, no passage/question/answer text) that picker screens (Practice's lesson-count grid, the subject/category availability check) read instead of fetching every category's full content up front. Regenerate it (along with the Tingxie/Stories indexes) with `npm run build-content-index` after hand-editing any content file — see `scripts/build-content-index.ts`. Don't hand-edit `index.yaml` files directly, they're derived.
  - **How `lessonIds` gets assigned, and why it differs by category.**
    - `pinyin`/`vocab`/`phrase`/`usage`: verified against each lesson's actual taught-vocabulary list. The "tested word" is extracted per format (the `__word__` marker for pinyin/phrase, the correct MCQ option's text for vocab, or the `（词语：X）` label — or, absent that label, the substring common to all 4 option sentences — for usage) and matched against a real per-lesson vocab list. A word taught in two lessons gets both lesson numbers (recycled vocab); a word not found in any lesson's list gets an empty `lessonIds` (so `lessonEligible` computes `false`) instead of a guessed lesson. Last done as a one-off pass (not an ongoing script) matching 178 questions against a 17-lesson vocab list the user supplied — see git history around the "practice by lesson" retagging commit for the method.
    - `conjunction`/`sentence`: **no such verification** — there's no single tested vocabulary word to match, since these test connector words (关联词, e.g. 要是……就/不但……而且) or sentence-logic completion. `lessonIds` is just whichever lesson the source exam paper as a whole was assigned (every question from one paper shares one value, e.g. all CH-paper questions got `[1]`, all NH-paper questions got `[2]`) — content-blind, and likely as inaccurate as pinyin/vocab/phrase/usage were before that pass. Fixing it would need a different reference (which conjunction pairs are taught in which lesson), not a vocab list.
- **`public/content/p5/tingxie/`** — one YAML file per lesson (`1.yaml`, `2.yaml`, ...) plus a generated `index.yaml` (`[{ id, title }]`). Same fields as before (`title`, `vocab[]`, `sentences[]`), except: each `vocab[]` entry now carries its own optional `sentenceBank: [{ zh, en }]` field (Apply's extra example sentences for that word) instead of a separate top-level `sentenceBank: Record<word, entries[]>` map — verified that every lesson's `sentenceBank` keys exactly matched its `vocab[].word` set before nesting it this way, so nothing was lost. `sentence.color` (a Tailwind class from the source app, never read by any code) was dropped entirely.
- **`public/content/p5/stories/`** — one Markdown file per lesson that has real content (`1.md`, ..., `17.md` — all 17 lessons are written today) plus a generated `index.yaml` (`{ written: [ids] }`; the lesson *count* comes from `meta.yaml` instead of being duplicated here). A lesson id with no `.md` file gets a client-side placeholder (`placeholderLesson()` in `data/stories.ts`) instead of a 404 — this is what lets the Read a Story picker always show every lesson button, real or "coming soon", without a network request for the not-yet-written ones. File format:
    ```markdown
    # 消失的"宝物"

    ## Page 1

    暑假到了，学校组织去森林露营、探险和攀岩。

    出发前老师提醒："带好袜子和手电筒来防止蚊虫。
    绝对不能单独行动，也禁止带贵重物品！"

    ## Page 2
    ...
    ```
    Parsed by a small hand-rolled splitter in `data/stories.ts` (not a CommonMark library): `# Title` on the first line, then one `## Page N` section per page, blank-line-separated paragraph blocks within a page, **one hand-split sentence per line** within a paragraph block (`StorySegment.paragraphs: string[][]`, each inner array one paragraph's sentences). Sentence splitting stays a one-time authorial choice, not a runtime regex — Chinese dialogue punctuation (a "…" quote spanning multiple sentence-ending marks) doesn't split cleanly with a generic rule (see Lesson 1's file for the convention: a quote that opens mid-sentence and doesn't close until the end of its own following sentence is still split at each 。！？, even though a sentence's closing quote mark ends up on the *next* line — harmless for read-aloud, since TTS doesn't vocalize quote glyphs differently anyway). Every page should have **at least 3 sentences** — a short paragraph gets merged onto a neighboring page rather than left alone as a sparse page (paragraph boundaries are still preserved for rendering, each renders as its own `<p>` in `Story.tsx`).
- **Migration/tooling scripts** (`scripts/`, run via `npx tsx scripts/<name>.ts`): `migrate-content.ts` was the one-off script that generated the files above from the old TS/JSON source the first time, and `migrate-question-schema.ts` was the one-off script that later flattened the question bank's on-disk shape (see the questions bullet above) — both kept for reference, not meant to be re-run against already-migrated content; `build-content-index.ts` is the ongoing one — **run `npm run build-content-index` after hand-editing any content file** so the three `index.yaml` files stay in sync with what's actually on disk.
- **Levels**: two levels exist today — `p5` (Primary 5, the full real content) and `p2` (Primary 2 — real, substantial content for `cloze`/`comprehension`/`pinyin`/`vocab`/`usage`, extracted from real exam papers across several Singapore P2 schools; the other six categories still just have their original 1-2-group hand-authored dummy content from before real P2 content existed). Adding another level (`p4`/`p6`/`sec1`/...) is just a new `public/content/<level>/` sibling directory with the same internal shape (`meta.yaml`, `questions/<category>.yaml` + generated `index.yaml`, `tingxie/<n>.yaml` + generated `index.yaml`, `stories/<n>.md` + generated `index.yaml`) plus one line in `data/levels.ts`'s `LEVELS` array — no other code change needed.
  - **Restricting a level to a subset of categories** (`LevelInfo.relevantCategories?: string[]`, `data/levels.ts`): P2 sets this to `["cloze", "comprehension", "pinyin", "vocab", "usage"]`, since its other six categories are still just dummy placeholder content, not something a P2 student should be able to select and practice. Omit the field (as `p5` does) for a level whose whole bank is real, offerable content. Two enforcement points, both reading `isCategoryRelevantForLevel(category, levelId)`:
    - **Picker UI** (`Practice.tsx`): `TYPE_PICKER_GROUP_DEFS` is filtered per-level into a `typePickerGroups` memo before rendering — a standalone-button category (e.g. Conjunctions) disappears from the grid entirely once filtered to zero categories, and the combined "词语运用 Vocabulary" button's underlying category list shrinks (e.g. P2 drops `"phrase"`, keeping `pinyin`/`vocab`/`usage`) without disappearing itself. `vocabularyCategoryKeys` (the filtered `VOCABULARY_CATEGORY_KEYS`) replaces the raw constant everywhere else in this file too (`vocabularySelected`, the lesson-count computation, the lesson-filter check) — using the unfiltered constant would make `vocabularySelected` permanently `false` on a level missing one of those four categories, since it'd wait forever for a category the UI never lets the student select.
    - **Session-building enforcement** (`lib/typeSession.ts`'s `selectTypeSessionGroups()`): filters out any candidate group whose category isn't relevant for `getCurrentLevel()` before sampling, as defense-in-depth beyond the picker UI — this is the one function all 3 `START_QUIZ` dispatch sites (Practice, Today's Mission, Special Quest) funnel through (see the MCQ-shuffle bullet above), so it guarantees an irrelevant category can never reach a built quiz session regardless of which UI path assembled the candidate groups. `TodayMission.tsx`'s `startLessonMission()` and `SpecialQuest.tsx`'s `vocab100` quest also pre-filter `VOCABULARY_CATEGORY_KEYS` themselves before fetching, purely to avoid a wasted fetch of an irrelevant category's content -- not required for correctness, since the enforcement layer already covers them.
    - **`AppStateContext.tsx`'s `vocabRetained()`** (decides whether `selectedLessons` survives a categories change) also filters `VOCABULARY_CATEGORY_KEYS` by the current `state.level` for the same reason `vocabularySelected` above needs it — checked against the unfiltered constant, it would never be satisfied on a level missing one of those categories, silently wiping the lesson filter on every categories change.
  - **`data/levels.ts`** is the level registry: `LEVELS: LevelInfo[]` (`{ id, label }`, shown by the level switcher), `DEFAULT_LEVEL` (`"p5"`), and a plain module-level `currentLevel` variable with `getCurrentLevel()`/`setCurrentLevel()`. This mutable variable — not a React Context — is what `data/questions.ts`/`data/tingxie.ts`/`data/stories.ts` read to build their fetch URLs (`content/<level>/...`) and cache keys, since those are plain async functions, not components. It exists *alongside* `AppState.level` (the React-visible copy used for rendering/reducer logic) rather than replacing it — the two are kept in sync by convention, never independently: every place that changes the level calls both `setCurrentLevel(id)` and `dispatch({ type: "SET_LEVEL", level: id })` together (currently only `components/common/LevelBar.tsx`'s click handler).
  - **Switching levels**: `components/common/LevelBar.tsx` renders a small chip-row switcher (reusing the `.chip`/`.chip-active` classes) below `TopNav`/`AccountBar` (`App.tsx`, same visibility rule as those — hidden during Quiz/Result/the Auth gate). It auto-hides itself when `LEVELS.length < 2`, so removing all extra levels back down to one silently removes the UI too, no separate flag needed. Clicking a level dispatches `SET_LEVEL`, whose reducer case (`AppStateContext.tsx`) resets to `{ ...initialState, level: action.level }` — every bootstrap/session/picker field (`questionIndexLoaded`, `questionIndex`, `categorySubjects`, `lessonCount`, `selectedSubject`, `selectedCategories`, `selectedLessons`, the quiz session) is wiped, since none of it carries over meaningfully to a different level's lessons/categories. `questionIndexLoaded` landing back at `false` is what makes `App.tsx`'s existing bootstrap `useEffect` (keyed on that flag) refire and fetch the new level's `meta.yaml`/`questions/index.yaml` automatically — no separate "level changed" effect was needed. `RESET_TO_HOME` explicitly preserves `level` (same as `selectedSubject` etc.) so a plain "back to home" click never silently reverts to `DEFAULT_LEVEL`. The chosen level is **not persisted** — a full page reload always comes back up on `DEFAULT_LEVEL` (`p5`); persisting it (e.g. alongside `isGuest` in `localStorage`) would be a natural follow-up if that turns out to matter.
  - **Cache isolation**: every module-level cache `Map` in the three data loaders is keyed by level (e.g. `` `${level}:${category}` `` in `data/questions.ts`'s `categoryCache`, similarly in `data/tingxie.ts`/`data/stories.ts`) — necessary because this is an SPA, so those `Map`s outlive a level switch; without level-prefixed keys, switching from P5 to P2 and back would serve P5's already-fetched P2-shaped cache slot (or vice versa) instead of re-fetching. The three fetch-function signatures themselves are unchanged (no `level` parameter) — every call site (`Practice.tsx`, `Story.tsx`, Tingxie's components, `App.tsx`'s bootstrap, the prefetch helpers) keeps working exactly as before, since the functions read `getCurrentLevel()` internally.
- **Prefetching / cache headers**: fetch-on-demand content is effectively instant on the Vite dev server (localhost round trips are sub-10ms), but on a real hosted deployment (this app is deployed to Vercel) each first-time fetch is a genuine network round trip and was noticeably slow (1-3s) the first time a student opened a screen — Practice's "开始练习" button, Tingxie's/Story's lesson buttons. Fixed with background warmup, not by changing the lazy-load contract itself: `data/questions.ts`'s `prefetchAllQuestionCategories()` (called once from `App.tsx` right after the bootstrap index lands), `data/tingxie.ts`'s `prefetchTingxieLessons()` (called from `LessonSelect.tsx` after its index loads), and `data/stories.ts`'s `prefetchStoryLessons()` (called from `Story.tsx` after its index loads) all fire-and-forget fetch every lesson/category into the same module-level cache Maps the real fetch functions already use, so a genuine click almost always resolves from cache instead of waiting on the network. Errors are swallowed (a failed prefetch just means the real click falls back to its own fetch/error handling). Also added `vercel.json` with a `Cache-Control: public, max-age=3600, stale-while-revalidate=604800` header on `/content/*`, so a repeat visit (even a fresh session, same browser) can skip the network entirely via HTTP cache rather than just the in-memory module cache, which only lasts one page load.

### Data layer (`src/data/`)
- `types.ts` — shared TypeScript interfaces for everything below: `Question` (`MCQQuestion | FillInQuestion | SelfCheckQuestion`), `QuestionGroup`, `QuestionIndexEntry` (the lightweight index-file shape, see above), `Passage`, `GroupResult`/`GroupResultItem`, `HistoryEntry` (`mode`/`categoryCounts` are optional — absent on pre-dashboard-redesign entries, every reader treats a missing value as "no data", never crashes), `PetState` (includes `questionsLifetime`, a lifetime count of individual questions answered, used for the "every 100 questions" achievement), `ShopItem`, `PetStage`, `MoodBucket`, `Achievement`/`AchievementType` (`"missionComplete" | "questionsMilestone" | "storyCompleted" | "specialQuestComplete"` — deliberately learning-only; feeding/evolving the pet is not tracked as an achievement, see `RecentAchievements` below), and the Tingxie content-shape interfaces `TingxieVocabItem`/`TingxieSentence`/`TingxieSentenceBankEntry`/`TingxieLesson`/`TingxieLessonIndexEntry` (see the Tingxie section below).
- `tingxie.ts` — Tingxie's data layer: `fetchTingxieLessonIndex()`/`fetchTingxieLesson()` (fetched from `public/content/p5/tingxie/`, parsed with the `yaml` package, cached in module-level `Map`s), `tingxieIconEmoji()`'s icon lookup, sentence/queue-building helpers (`tingxieSentenceWords`, `tingxieBlankWord`, `buildTingxieApplyQueue`, `buildTingxiePracticeVocabQueue`/`buildTingxiePracticeSentenceQueue`, `pooledTingxieReview`), and the `TingxieApplyItem`/`TingxiePracticeItem` queue-item types. `buildTingxieApplyQueue(vocab)` takes a `TingxieVocabItem[]` (each item's own optional `sentenceBank` field) rather than the old standalone `Record<word, entries[]>`. `pooledTingxieReview(lessons)` returns `{ vocab, sentences, applyVocab }` — `vocab`/`sentences` are capped samples for Learn's carousel (`TINGXIE_REVIEW_VOCAB_COUNT`/`TINGXIE_REVIEW_SENTENCE_COUNT`), `applyVocab` is the full uncapped merged vocab pool Apply's queue is built from (see the Tingxie section below for why this needs to stay uncapped).
- `stories.ts` — "Read a Story" mode's data loader: `fetchStoryIndex()` (fetches `meta.yaml` + `stories/index.yaml`, returns `{ lessonCount, written }`) / `fetchStoryLesson(id)` (fetches and parses one lesson's Markdown, or synthesizes `placeholderLesson(id)` if its id isn't in `written`), plus the `StoryLesson`/`StorySegment` types and `segmentSentences()` helper. Both cached in module-level `Map`s, same pattern as `tingxie.ts`. See the Content files section above for the Markdown format/parsing rule.
- `questions.ts` — the question data **loader** (not the data itself, see Content files above). `CATEGORIES` (map of category key → `{ label, lessonMode }`; `lessonMode: true` categories are single-sentence items eligible for lesson-filtering, `lessonMode: false` are passage-based items that never take a lesson filter), `VOCABULARY_CATEGORY_KEYS` (`["pinyin", "vocab", "phrase", "usage"]`, the 4 categories the Practice screen combines into one "词语运用 Vocabulary" button), and `SUBJECTS` (e.g. `["Chinese", "Higher Chinese"]`) stay plain constants — stable app config, not per-level content. `fetchQuestionMeta()`/`fetchQuestionIndex()`/`fetchQuestionCategory(category)` fetch+cache the actual content (module-level `Map`s again); `fetchQuestionCategory()` is also where the dropped `qNo`/`lessonEligible` fields get synthesized back onto each group/question, see Content files above. `computeCategorySubjects(index)` is a pure function (`Record<category, Set<subject>>` — which subjects actually have at least one group of each category; Higher Chinese currently only has `cloze`/`errorcorrect`/`comprehension`) that used to be a module-eval-time constant (`CATEGORY_SUBJECTS`) derived from the old bundled `QUESTION_GROUPS` array — now it's computed once from the fetched index and stored in `AppState` (see below), since a plain export can't depend on an async fetch.
- `pet.ts` — pet/BP tunable config (not per-user state):
  - `PET_STAGES` — 6 growth stages (egg/baby/toddler/young/teenager/adult) with `minAgeYears` thresholds (0/3/7/11/16/21).
  - `GROWTH_PER_AGE_YEAR` (100, see the age note below), `MOOD_DECAY_PER_HOUR`.
  - `BP_AWARD` (per question format), `TINGXIE_BP_AWARD` (per Tingxie activity, see the Tingxie section), `MISSION_COMPLETE_BONUS_BP` (one-time-per-day bonus for finishing all 3 Today's Missions, see `TodayMission`).
  - `SHOP_ITEMS` (id/cost/growth/mood — a toy's `mood` is its *maximum* possible payout, see `TOY_GAMES`) and `TOY_GAMES` (one minigame config per toy `ShopItem.id`, see the Toy minigames section).
  - `SPECIAL_QUEST_TYPES`/`specialQuestConfig()` — the Home dashboard's Special Quest wheel, see the `SpecialQuest` bullet in Screens and `state/specialQuest.ts`.
  - `PET_DEFAULT_STATE` and the owl-art helpers described below.
  - **Age**: purely a derived display/evolution concept, never stored — `state/PetContext.tsx`'s `getAge(growth)` is `Math.floor(growth / GROWTH_PER_AGE_YEAR)`. Growth itself is unchanged (still only earned by feeding, via `giveItem()`, exactly as before); age is just a friendlier framing of the same number (100 growth = 1 "year"), and `getStage()`/`nextStage()` now compare age against each `PetStage.minAgeYears` instead of comparing raw growth against a raw threshold. This made stage thresholds ~10x larger in growth-point terms than before (adult used to be 200 growth, now 2100 = 21 years × 100) — feeding paces/item costs are unchanged, so reaching Adult now takes proportionally longer. Shown next to the stage label on the Owl screen and `PetHeroCard` (e.g. "🎂 4岁"). **Deliberately not shown**: how many years until the next stage — the growth bar (`PetStatBars`, `PetHeroCard`) only ever shows progress within the *current* age year (`growth % GROWTH_PER_AGE_YEAR`, always 0-100), never `PetStage.minAgeYears`, so a curious kid can't read off exactly when the next evolution lands. Every time growth crosses a 100-point boundary (`giveItem()`'s returned `agedUp`), `Bag.tsx` plays `Sound.levelUp()` and shows a celebratory age-up banner — see the Bag bullet below and Sound section.

### App state layer (`src/state/AppStateContext.tsx`)
`useReducer` + two React Contexts (`AppStateCtx`/`AppDispatchCtx`, read via `useAppState()`/`useAppDispatch()`). `AppState` holds `screen` (`"home" | "practice" | "quiz" | "result" | "owl" | "shop" | "bag" | "play" | "tingxie" | "story" | "auth"`), the current quiz session (`mode`, `modeLabel`, `groups`, `groupIndex`, `results`, `submitted`), picker selections (`selectedSubject`, `selectedCategories`, `selectedLessons`), `playingItemId` (which toy's `ShopItem.id` is active on the `"play"` screen — see the Toy minigames section below), and the question-bank bootstrap data — `questionIndex`, `categorySubjects`, `lessonCount`, `questionIndexLoaded` (see below). `App.tsx`'s `ScreenRouter` switches on `state.screen` to render the matching component from `src/components/`. `"auth"` is a routed-to placeholder for a not-yet-built login screen. `"story"` is the sole entry point into Read a Story (`Story.tsx`) — like Tingxie, everything past that (which lesson, which page) is local `useState` inside `Story.tsx`, not further `AppState`/actions; unlike Tingxie it doesn't even need its own reducer/Context, since the local state is just two numbers (see the Read a Story section below).

**Question-bank bootstrap**: since question content now lives in `public/content/` and is fetched at runtime (see Content files above) rather than bundled, `App.tsx`'s `ScreenRouter` fetches `meta.yaml` + `questions/index.yaml` once on mount (before rendering any actual screen — it shows a `加载中... Loading...`/retry-on-error screen in the meantime) and dispatches `SET_QUESTION_INDEX` with the result. This populates `questionIndex` (the raw `QuestionIndexEntry[]`), `categorySubjects` (`computeCategorySubjects(index)`, `data/questions.ts`), `lessonCount`, and flips `questionIndexLoaded` to `true`. This has to live in `AppState` (not a separate Context) specifically because `SELECT_SUBJECT` below reads `categorySubjects` **synchronously inside the reducer** — a reducer can't `await` a fetch or read React Context, so the data has to already be sitting in `state` by the time that action is dispatched. `RESET_TO_HOME` explicitly preserves all four bootstrap fields (same as `selectedSubject`/`selectedCategories`/`selectedLessons`) so every "back to home" click doesn't wipe them and re-trigger the bootstrap fetch.

Quiz session actions: `START_QUIZ`, `SUBMIT_GROUP`, `UPDATE_ITEM_RESULT` (patches one self-check item's result in place after the student clicks a self-check button — see below), `NEXT_GROUP`, `RESET_TO_HOME` (mirrors the old app's `resetToHome()`: clears session state but keeps `selectedSubject`/`selectedCategories`/`selectedLessons`/the bootstrap fields above). `START_PLAY` (sets `screen: "play"` + `playingItemId`, dispatched from `Bag.tsx` when a toy's "Play" button is clicked — see the Toy minigames section below).

Picker actions: `TOGGLE_CATEGORY` (single category key), `TOGGLE_CATEGORY_GROUP` (an array of keys, toggled as one unit — all-selected → deselect all, otherwise select all; used by `Practice.tsx`'s combined "词语运用 Vocabulary" button, see below), and `SET_CATEGORIES` (full replace — used by Today's Mission's "词语复习" card to jump straight to a clean Vocabulary-only selection). `SELECT_SUBJECT` also prunes `selectedCategories` down to only categories `state.categorySubjects` says exist for the newly-picked subject, so switching to Higher Chinese silently drops an already-selected Chinese-only category instead of leaving it selected-but-greyed-out.

Lesson-filter actions: `TOGGLE_LESSON`/`SELECT_ALL_LESSONS` toggle `selectedLessons: Set<number>`, where **empty means "all lessons"** (the default — no filter) rather than "none". Any action that changes `selectedCategories` (`SELECT_SUBJECT`, `TOGGLE_CATEGORY`, `TOGGLE_CATEGORY_GROUP`, `SET_CATEGORIES`) also resets `selectedLessons` back to empty whenever the result no longer has all of `VOCABULARY_CATEGORY_KEYS` selected (`vocabRetained()` helper) — a lesson filter left over from a since-deselected Vocabulary would otherwise sit there silently.

### Screens (`src/components/`)
Each top-level screen is its own component/folder: `Home`, `Practice`, `Quiz`, `Result`, `Owl`, `Shop`, `Bag`, `Play`, `Tingxie`, `Story` (see below). Shared UI lives in `components/common/`: `Modal.tsx` (`ConfirmModal` — a custom in-page confirm dialog, used instead of `window.confirm` so styling/behavior stays consistent, e.g. leaving a quiz mid-session or clearing history), `OwlArt.tsx` (see Owl art below), `TopNav.tsx` (see below), and `CompleteScreen.tsx` (a full-page 🎉 celebratory screen — `title`, optional `bpAmount` rendered as a `.bp-pop` "+N BP" line, optional `children` for extra content below, e.g. a "back" button — rendered in place of an activity's normal content once it's finished; shared by Tingxie's Learn/Apply/Practice and Read a Story, see those sections below, using the generic `.complete-screen`/`.complete-emoji` CSS classes, not `tingxie-`-prefixed ones, since it's no longer Tingxie-only).

- **`common/TopNav.tsx`**: a persistent top nav (`.top-nav`, `position: sticky; top: 12px`), plain Chinese-only text labels (no icons/English subtitles) with 5 items — 主页 Home (`RESET_TO_HOME`, same as every other "back to home" affordance in the app), 听写练习 (→ `"tingxie"`), 练习 Practice (→ `"practice"`), 读故事 Read a Story (→ `"story"`), 宠物 Pet (→ `"owl"`, and stays highlighted while on `"shop"`/`"bag"`/`"play"` too, since those are reached from the pet flow). `App.tsx`'s `ScreenRouter` renders it above every screen **except** `"quiz"`/`"result"` — a quiz in progress already has its own Home button with a "leave without saving?" confirmation (see the Quiz bullet below), and an always-visible second way to navigate away would either bypass that confirmation or need to duplicate it, so it's simplest to just not show it there.

- **Practice** (`Practice.tsx`, screen `"practice"`): the single entry point for both question-type and lesson-based practice (previously two separate screens/pickers — merged into one).
  - **Question type section** ("选择题型 Select Question Type"): unchanged from the old Type Picker — a subject row (All/Chinese/Higher Chinese chips) and a `category-grid` of `TYPE_PICKER_GROUPS` buttons (Pinyin/Vocabulary/Phrase Meaning/Correct Usage combined into one "词语运用 Vocabulary" button via `TOGGLE_CATEGORY_GROUP`, every other category its own button), each greyed out/disabled (`.category-disabled`) when `groupApplicable()` says none of its categories exist under the selected subject (backed by `state.categorySubjects`, populated at app bootstrap — see the App state layer section above).
  - **Lesson section** ("选择课文 Select Lesson(s)"): a `.lesson-grid` of chips (an "全部课文 All Lessons" chip plus one per `state.lessonCount`, each showing how many Vocabulary-category questions match under the current subject via `state.questionIndex`, greyed out at 0) — only interactive once Vocabulary's 4 categories are all selected (`vocabularySelected`); otherwise every chip is `disabled` and a `.picker-hint` explains why. Selecting specific lesson(s) restricts *only* the Vocabulary categories' candidate pool to groups whose `lessonIds` include one of the chosen lessons — every other selected category (conjunction, sentence, cloze, ...) is unaffected, since only Vocabulary's `lessonIds` were verified against a real vocab list (see the `lessonIds` note above).
  - **Starting a session**: "开始练习 Start Practice" first `await`s `fetchQuestionCategory()` (`data/questions.ts`) for every selected category — the button shows a brief "加载中... Loading..." state while this resolves, since full question content isn't fetched until a session is actually about to start (only the lightweight index is loaded up front, see the App state layer section above) — then runs the same `selectTypeSessionGroups()` sampling as before (one passage per passage-category, individual categories pooled and capped) on the combined result. A lesson filter only narrows Vocabulary's candidate pool going in, it doesn't change how many questions come out. The resulting session's `mode` is `"lesson"` only when the student genuinely narrowed away from the "all lessons" default (`selectedLessons.size > 0`); otherwise it's `"type"`, same as a plain type-only session — this is what keeps Today's Mission's "词语复习" card (`isLessonMissionComplete`, checks for a `mode: "lesson"` history entry today) working unchanged.
  - **Passage selection is round-robin, not pure random**: `lib/typeSession.ts`'s `pickRoundRobin()` persists a per-category shuffled queue of not-yet-served group ids to `localStorage` (`hanyuPracticePassageRotation_v1`) — every passage in a category is served once before any repeat, then the queue reshuffles for a new cycle, so a student practicing the same category repeatedly cycles through every available passage instead of a plain `Math.random()` pick re-showing the same one or two by chance. The queue is filtered to currently-valid ids on every draw, so it self-heals if the candidate set changes (a different subject filter, or new questions added to a category's file).
  - **MCQ option order is randomized fresh per session**, not authored/fixed: `lib/typeSession.ts`'s `selectTypeSessionGroups()` runs every group it returns through `lib/mcqShuffle.ts`'s `shuffleMcqOptions()` (the only place that needs to call it, since all 3 `START_QUIZ` dispatch sites — Practice, Today's Mission, Special Quest — funnel through this one function) — shuffles either the group's shared `optionBank` (dialogue-completion groups, so the "词语库 Word Bank" box and every question's compact radios stay in sync, since both render structurally from `optionBank`) or each MCQ question's own `options`, reassigns keys `"1"`/`"2"`/... in the new order, and remaps `correctKey` to match. Always returns new objects (never mutates in place), since `fetchQuestionCategory()` caches fetched groups in a module-level `Map` reused by every future session — mutating a cached group would freeze its shuffle after first use instead of re-shuffling each time.

- **Quiz** (`Quiz.tsx`): groups for the session are shuffled once (`lib/shuffle.ts`) and stepped through one at a time via `state.groupIndex`. Submitting a group calls `gradeGroup` (`lib/grading.ts`), which grades MCQ/Fill-in immediately and returns self-check items (Long-Answer/Writing-Constrained) as `correct: null` until the student clicks a "✓ 我答对了 / ✗ 还需加强" button, which dispatches `UPDATE_ITEM_RESULT`. Each question has a "🔊 听写 Dictation" button (`lib/speech.ts`'s `speakText()`, `SpeechSynthesisUtterance` in `zh-CN`) that reads the question aloud; a group with a passage (`group.passage`, i.e. Cloze/Error Correction/Comprehension/Dialogue/Practical Text) additionally shows its own dictation button in the passage box's header (`.passage-head`, rendered by the `PassageBox` sub-component) that reads the full passage text, separate from each question's own button — since passages run long, this button toggles into a "⏹ 停止 Stop" button (`speakText()`'s optional `onDone` callback, fired whether the reading finishes naturally or is interrupted) rather than just firing once like the per-question buttons. `speakText()` always `cancel()`s any prior utterance before starting a new one, but that alone doesn't stop a reading that's still playing when the student just moves on without triggering new speech; `Quiz.tsx` additionally calls `speech.ts`'s `stopSpeaking()` explicitly in `handleSubmit()` and on every `state.groupIndex` change/unmount, so a reading never bleeds into a question the student has already left. **Auto-advance:** if every item in a submitted group graded `correct === true` outright, the quiz auto-dispatches `NEXT_GROUP` after a 0.8s pause (with a visible "moving on..." hint on the Next button); anything wrong/skipped, or still awaiting a self-check click, requires the manual click. A pending auto-advance is cancelled if the student clicks Next early or navigates to a new group.
- **Result** (`Result.tsx`): computes the session score, saves it to history (`state/history.ts`, including `mode`/`categoryCounts` for the dashboard below) once on mount, plays `Sound.applause()` on a score of 90% or higher or `Sound.encourage()` otherwise.
  - **Same once-per-mount effect** also: calls `usePet().recordQuestionsCompleted()`, logs any newly-crossed `questionsMilestone` achievement, calls `state/achievements.ts`'s `checkAndAwardMissionBonus()` (see `TodayMission` below), and checks the Special Quest wheel's `vocab100`/`comprehension1` completion (see `SpecialQuest` below) — `vocab100` needs every group's `category` in `VOCABULARY_CATEGORY_KEYS` and `correctItems === totalItems` (raw counts, not the rounded display `pct`, so a near-100% session can't false-positive); `comprehension1` needs every group's `category === "comprehension"`, any score. A match calls `state/specialQuest.ts`'s `completeSpecialQuest()` (the dedup guard) and, only if that returns true, `awardBP()` + `logAchievement({ type: "specialQuestComplete" })`, shown inline as a `.quest-bonus-banner`. This fires for *any* qualifying session finished that day, not only one launched via the wheel's own "Do Quest" button. The effect is guarded by a `ranRef` (not just an empty dep array) because React 18 StrictMode double-invokes empty-dep effects once on mount in dev, and unlike the old idempotent `saveHistory`-only version, achievement logging is not idempotent.
  - **PDF export**: for `state.mode === "type"` sessions only, shows a "🖨️ 打印 / 存为 PDF Print / Save as PDF" button (`lib/exportPdf.ts`'s `exportSessionToPdf()`) that renders the whole session (passages, word banks, every question with the student's answer vs. the correct/model answer) into a **new tab** (`window.open("", "_blank")`, called synchronously in the click handler to dodge popup blockers) and calls `print()` on it after a short `setTimeout`, so the student saves it via the browser's print dialog — deliberately not a PDF-generation library, to avoid embedding a CJK font just for Chinese text. Used to write into a hidden 0×0 `<iframe>` instead; switched to a real new tab because iOS/iPadOS Safari does not reliably fire `print()` on a hidden iframe's `contentWindow` (the dialog silently never opens) — don't revert to the iframe approach. This is what `GroupResultItem.answer` (`data/types.ts`) exists for: `lib/grading.ts`'s `gradeQuestion()` keeps the student's raw MCQ key / typed text on the result item instead of discarding it after grading.
- **Home** (`Home.tsx`): a dashboard, not just a mode picker. Top to bottom: `PetHeroCard` (see below — this is the first section, no separate greeting above it), `SpecialQuest` (see below), `TodayMission`, the Continue Learning section (three `.mode-row` buttons — icon, Chinese title + English subtitle, a trailing "›" — **Dictation Practice first**, then the combined Practice screen, then Read a Story; stacked full-width rows, not a card grid, so this section reads as the same "things to do today" shape as `TodayMission` right above it), the `.today-summary-card` (see below), then `RecentAchievements` — the dashboard's last section. **Every `.dash-card` has exactly one heading** (`<h2 className="section-heading">`, styled in `--gold-deep`) — there used to also be a small `.section-eyebrow` kicker line stacked directly above it (e.g. TodayMission's eyebrow and heading both literally said "Today's Mission"), which read as a duplicated header; that class is gone, don't reintroduce it.
- **`.today-summary-card`** (inline in `Home.tsx`, no separate component file): a "🖨️ 打印 / 存为 PDF Print / Save as PDF" button for `lib/exportPdf.ts`'s `exportTodaySummaryToPdf(hist)` — a same-day aggregate PDF, distinct from Result.tsx's single-session one. Only rendered when there's something to show (`getTodayStats(hist).questions > 0 || isTingxieMissionComplete()`), so an empty dashboard doesn't offer a pointless button. See `state/todaySummary.ts` below for what feeds it. Besides `todaySummary.ts`'s own stores (practice sessions, Tingxie misses, stories read), this PDF also reads `state/achievements.ts`'s `loadAchievements()` directly, filtered to today's `"tingxieCompleted"` entries via `state/achievements.ts`'s `parseTingxieCompletedDetail()` — a small table of which lesson + which activity (Learn/Apply/Test) the student completed today, the same underlying data `RecentAchievements.tsx` renders on the dashboard itself, just re-sourced here so the PDF doesn't need its own parallel "completions today" store.
- **`PetHeroCard.tsx`**: the pet art is the centerpiece, not a small thumbnail beside stats — and the greeting that used to be Home's own separate top section (`greeting()`'s time-of-day text + a `getTodayStats(hist)`-derived subgreeting) is now *merged into this card* rather than living above it, so the greeting and the pet read as one visual unit. ### Toy minigames (`src/components/Play/`)
Playing with the pet, as opposed to feeding it: each of the 3 toy `SHOP_ITEMS` (`ball`/`kite`/`puzzle`) has a matching minigame config in `data/pet.ts`'s `TOY_GAMES` (keyed by `ShopItem.id`) instead of the flat instant-mood effect food items get. Reached only from `Bag.tsx`'s toy cards (see the Bag bullet above) — there's no Play entry point from the Shop.

- **Flow**: tapping a toy card in the Bag calls `usePet().consumeItem(item)` (removes it from inventory right away — same "irreversible once started" rule as feeding, so abandoning the game mid-play still costs the item, no refund) and dispatches `START_PLAY`, which routes to `"play"` (`PlayGame.tsx`). `PlayGame` looks up the item + its `TOY_GAMES` config and renders the matching game component (`components/Play/types.ts`'s `GameProps`), passing it `onComplete(result: GameCompletion)` and `onExit()`. `onExit` (the game's back button) just navigates back to `"bag"` with no reward — the item's already gone, matching the "consumes regardless of outcome" decision. `onComplete` is the only path that grants a reward.
- **`GameCompletion` contract** (`components/Play/types.ts`): every game reports `{ perfect: boolean; scoreLabel: string }` regardless of what it internally measures — a round-based game (hits out of attempts) and a timed game (elapsed seconds) compute "was this a bonus-earning run" very differently, but both collapse to the same two fields, so `PlayGame.tsx` never needs to know which kind of game produced them. `scoreLabel` is just for display on the result screen (e.g. `"5 / 5"` vs `"0:38"`).
- **Reward math** (`PlayGame.tsx`'s `handleComplete`): flat completion reward always applies once a game reports completion at all (`config.flatMood`, regardless of how close to "perfect" it was); a `perfect: true` result adds `config.bonusMood` on top. `flatMood + bonusMood` always equals the toy's `ShopItem.mood` (its Shop/Bag "max" stat), so the toy economy didn't need rebalancing when this replaced the old instant-give. `usePet().applyPlayReward(item, moodReward)` applies the toy's full `item.growth` (always granted, unlike mood — every `SHOP_ITEMS` toy has a small nonzero value, see the Bag bullet above) + the computed mood, and returns `{ agedUp, age }`, same shape as `giveItem()` — `PlayGame` shows the same kind of age-up messaging inline in its result card (not `Bag.tsx`'s `.age-up-banner`, since the student isn't on the Bag screen at that moment) rather than reusing it. `Sound.applause()`/`Sound.encourage()` play on a perfect vs. non-perfect result, same semantics as a Quiz/Tingxie session scoring ≥90%/<90%. `handleComplete` also checks the Special Quest wheel here (see `SpecialQuest` in Screens above): `ballPlay` completes on `item.id === "ball"` with any `completion` (no score bar); `memoryFast` completes on `item.id === "puzzle" && completion.perfect` (`config.bonusTimeSeconds` = 20s already *is* "perfect" for this toy, so no separate time check is needed). A match calls `state/specialQuest.ts`'s `completeSpecialQuest()` (the dedup guard) and, only if that returns true, `awardBP()` + `logAchievement({ type: "specialQuestComplete" })`, shown inline in the result card as `.play-result-quest-bonus`.
- **`TOY_GAMES` has two config shapes** sharing one flat (non-discriminated-union) `ToyGameConfig` interface: round-based games (`attempts`/`bonusThreshold`) and the timed memory game (`pairCount`/`bonusTimeSeconds`). Every field but the common `flatMood`/`bonusMood`/`bonusLabel` is optional on the type, and each game component reads the ones that apply to its own `game` id with a non-null assertion (`config.attempts!`, etc.) — the fields are never actually missing for a real toy's config, this is just what keeps one `Record` type instead of a discriminated union with per-game prop narrowing at the `PlayGame.tsx` `switch` call sites.
- **`ball` → `CatchGame.tsx`** (`config.game === "catch"`): the marker sweeps back and forth across a track via a plain CSS keyframe animation (`.catch-marker`/`@keyframes catch-sweep` in styles.css), restarted each round by remounting the marker element with `key={attempt}` (a fresh `animationDuration` per round is what ramps up the difficulty) — deliberately **not** a `requestAnimationFrame` + React state loop driving the position; an earlier version did that and the marker silently stalled/never appeared to move for real users, an easy failure mode for a per-frame state loop (e.g. a StrictMode double-effect edge case) that a pure CSS animation isn't subject to. Tap "🎾 接住！Catch!" while it's inside a randomly-placed highlighted zone — hit detection reads the marker's actual on-screen position at tap time (`getBoundingClientRect()`) rather than any JS-tracked position, so it can never drift out of sync with what's rendered. `config.attempts` (5) rounds, `config.bonusThreshold` (5, i.e. a genuine 5/5) for the bonus.
- **`kite` → `FeatherGame.tsx`** (`config.game === "feather"`): one feather at a time falls from a random x position (same CSS-keyframe-restarted-by-remounting-with-`key={attempt}` pattern as `CatchGame`'s marker, see above — a fresh `animationDuration` per round ramps up the fall speed). Unlike the ball game, there's no separate "Catch!" button — the falling feather (a `<button>`) *is* the tap target, so tapping it early is always a hit; letting its fall animation finish untapped (`onAnimationEnd`) is an automatic miss. Both paths resolve through one `resolve(isHit)` guarded by `lockedRef` so a tap and a same-instant natural animation-end can't both score the round. `config.attempts` (8) rounds, `config.bonusThreshold` (7, i.e. 7 or 8 of 8) for the bonus.
- **`puzzle` → `MemoryGame.tsx`** (`config.game === "memory"`, `ShopItem.id` deliberately still `"puzzle"` even though the game itself is now a card-matching memory game, not a leaf-picking guess — keeps existing bagged/purchased inventory keys valid): `config.pairCount` (6) pairs, 12 cards total in a 4x3 grid, flipped via a 3D `perspective`/`rotateY` card-flip (`.memory-card`/`.memory-card-face`, same visual technique as Tingxie's flip cards). Flip two at a time; a match (`Sound.ding()`) stays face-up permanently, a mismatch (`Sound.miss()`) flips back after `MISMATCH_PAUSE_MS` (800ms). There's no fail state — the deck is always eventually solved — so completion (a `useEffect` watching `matchedPairs`, guarded by `doneRef` so it only fires once) always earns the flat reward; a live timer (`elapsedMs`, ticked every 200ms from a `performance.now()` start captured on mount) decides `perfect` via `config.bonusTimeSeconds` (20s) instead of a hit count, reported as the `mm:ss` `scoreLabel`.
- **`PlaceholderGame.tsx`** is a pure fallback (every current toy has a real game) for any future `TOY_GAMES` entry added before its game component exists — claims the flat reward only (`onComplete({ perfect: false, scoreLabel: "—" })`) rather than leaving a purchase wasted, wired in `PlayGame.tsx`'s `switch` `default` case.
- **Shared round-UI CSS** (`.play-round-progress`/`.play-round-feedback*`/`.play-round-hits` in styles.css): the "round N / total", hit/miss feedback line, and running hit/match tally are visually identical across `CatchGame`/`FeatherGame`/`MemoryGame`, so all three render some subset of these shared classes — only the "arena" in between (`.catch-track`/`.catch-marker`/`.catch-zone`, `.feather-sky`/`.feather-target`/`.feather-ground`, or `.memory-grid`/`.memory-card`) is game-specific. Reuse these for any future toy game rather than inventing new per-game equivalents.

### Read a Story (`src/components/Story/Story.tsx`)
A fourth top-level practice mode, entered via a `.mode-row` on Home or the TopNav's "读故事" tab (`GO_TO_SCREEN "story"`) — **deliberately independent of the Quiz/Result/`QuestionGroup` pipeline**, same reasoning as Tingxie: it's not a graded activity, just a reading/read-aloud tool, so it doesn't touch history/achievements/Today's Mission. It does have **one** BP hook though (see the Finish bullet below).

- **Local state, single file, no reducer**: everything (`view: "picker" | "reading" | "complete"`, `lessonId`, `segmentIndex`) is plain `useState` inside `Story()` — no `TingxieProvider`-style local Context/reducer, since there's no queue mechanic or multiple activities to coordinate here, just two numbers plus a view flag. `StoryReader` (the reading view) is a **separate top-level function**, not nested inside `Story()`'s body — nesting it would give React a new component identity every render and force a full remount on every parent re-render, wiping its `segmentSpeaking` toggle state each time (same reasoning as `Quiz.tsx`'s `PassageBox` being defined outside `Quiz()`).
- **Finishing a story** (`view: "complete"`): a real (non-`placeholder`) lesson's last page shows a "🎉 我读完了 Finish Reading" button (`.story-finish-row`, centered below the page text, in place of the missing next-page curl) instead of `StoryReader`'s usual curl-based navigation. Clicking it (`Story()`'s `finishStory()`) awards a flat `STORY_COMPLETE_BP_AWARD` (10, `data/pet.ts`) via `usePet().awardBP()`, plays `Sound.applause()`, and switches to `view: "complete"`, which renders `common/CompleteScreen.tsx` with a "← 返回课文列表 Back to Lessons" button. A `placeholder` "coming soon" stub lesson gets **neither** the Finish button nor any next-page affordance on its one page — there's nothing to genuinely finish, and letting every not-yet-written lesson award BP for one tap would make the reward trivially farmable. This is Read a Story's only BP hook; nothing else about finishing a story touches history/achievements/Today's Mission. All 17 lessons have real content today (see `public/content/p5/stories/`), so this placeholder path isn't currently exercised, but it's what any future lesson beyond what's been written falls back to.
- **Lesson picker** (`view: "picker"`): a `.lesson-grid` of lesson buttons, sized from `fetchStoryIndex()`'s `lessonCount` (fetched on mount into local `storyIndex` state, with its own loading/retry-on-error UI — same `LOAD_INDEX_START/SUCCESS/ERROR`-shaped idiom as Tingxie's `LessonSelect.tsx`, just as plain `useState` instead of a reducer action), same classes as Tingxie's `LessonSelect.tsx` and Practice's lesson picker (`.lesson-btn`/`.lesson-btn-num`). A lesson id not in `storyIndex.written` shows a "敬请期待 Coming soon" badge (reusing `.lesson-btn-count`) but is still clickable — clicking it calls `fetchStoryLesson(id)`, which synthesizes a one-page "coming soon" stub client-side (no network request for an unwritten lesson) rather than the picker disabling it, so the picker doesn't need to special-case unwritten lessons visually beyond the badge.
- **Reading view** (`view: "reading"`): pages through `lesson.segments[segmentIndex]` one page at a time. Every page groups one or more of the story's original paragraphs so it has **at least 3 sentences** (a lone short paragraph gets merged onto a neighboring page rather than left as its own sparse page) — paragraph boundaries are still preserved for rendering (`StorySegment.paragraphs: string[][]`, each inner array one paragraph, each rendered as its own `<p className="story-paragraph">`), so a page can show more than one paragraph without losing the story's original line breaks. `data/stories.ts`'s `segmentSentences(segment)` flattens a page's paragraphs into one sentence list where a flat list is what's actually needed (the segment-level dictation button, page-length checks).
- **Page-turn navigation**: a curled-paper-corner button in the page's bottom-right (`.story-page-curl-next`) flips forward, bottom-left (`.story-page-curl-prev`, the same shape mirrored via `scaleX(-1)`) flips back — no plain "Prev"/"Next" text buttons. Each corner only renders when that direction actually goes somewhere (first/last page have no wraparound). Clicking one runs `StoryReader`'s `flipTo(direction)`, a two-phase animation sequenced entirely in JS (`FLIP_MS` = 260ms per phase): phase "out" rotates the current page away in 3D (`.story-page-flip-{next,prev}-out`, `transform-origin` on the corresponding edge) via a `setTimeout` matching `FLIP_MS`; once that fires, `segmentIndex` actually advances and phase "in" rotates the new page into place from the opposite extreme (`.story-page-flip-{next,prev}-in`) via a second matching `setTimeout`. One content slot plays both halves in sequence rather than rendering two full pages layered on top of each other, which keeps the state machine simple (`flip: { direction, phase } | null`) at the cost of a strict "can't start a new flip until the current one finishes" (`if (flip) return;` guard, also `disabled` on both curl buttons while `flip !== null`). The `.story-page-flipper` wrapper supplies `perspective` for the 3D effect; the animations are gated behind `@media (prefers-reduced-motion: no-preference)` so a reduced-motion student just gets an instant page swap at the same JS-timer cadence, no visual rotation.
- **Two independent read-aloud affordances per page**, both via `lib/speech.ts`'s `speakText()`/`stopSpeaking()`:
  - A page-level "🔊 朗读本段 / ⏹ 停止" toggle button (`.dictation-btn`/`.dictation-btn-active`, identical pattern to Quiz.tsx's `PassageBox`) that reads every sentence on the page concatenated together, and can be stopped mid-read by clicking it again.
  - Each individual sentence is its own tappable `<button className="story-sentence">` (full button-chrome reset, `display: inline` so sentences still flow together as one paragraph) — clicking one reads *only* that sentence via a plain one-shot `speakText(sentence)` call, no toggle state of its own.
  Clicking a sentence while the page-level reading is in progress interrupts it (`speakText()` always cancels any prior utterance first) and immediately resets the page-level button back to its "🔊" state (an explicit `setSegmentSpeaking(false)` right before the call, not just relying on the async `onDone` callback, so the button's visual state doesn't lag behind the click). `Story.tsx`'s top-level `useEffect` also calls `stopSpeaking()` on every lesson/page/view change and on unmount, same lingering-speech fix as Quiz.tsx/Tingxie's shell-level guard.
- **Sentence data is hand-authored, not runtime-split** — see the `data/stories.ts` bullet above for why (Chinese dialogue punctuation doesn't split cleanly with a generic 。！？ regex once quotes are involved).

### Tingxie / 听写 dictation practice (`src/components/Tingxie/`)
A third top-level practice mode, entered via a `.mode-row` on Home (`GO_TO_SCREEN "tingxie"`) — **deliberately independent of the Quiz/Result/`QuestionGroup` pipeline**. It was ported from a separate standalone app (functionality only, not its Tailwind styling or its points-ledger system) and reuses this app's BP/pet economy instead of a second reward system.

- **Local state, not global**: `Tingxie.tsx` mounts its own `TingxieProvider` (`tingxieState.tsx` — a `useReducer` + two Contexts, `useTingxieState()`/`useTingxieDispatch()`, same shape as `AppStateContext.tsx` but scoped entirely to this subtree). `AppStateContext`'s `Screen` union only knows about a single `"tingxie"` entry point; everything that happens after that (lesson selection, which of the 3 activities is active, flip/queue progress) lives in this local reducer and is **not persisted** — leaving the mode resets it, by design (no localStorage key for it). The one deliberate exception is a single timestamp in `state/tingxieProgress.ts`, marking that *some* activity completed today — just enough for Home's Today's Mission to see it after the fact (see below), without persisting anything about *which* lesson/activity.
- **Stops its own read-aloud on navigation**: `Tingxie.tsx`'s shell calls `speech.ts`'s `stopSpeaking()` whenever `view`/`subTab`/`activeContent` changes or the component unmounts — the same lingering-speech fix as Quiz.tsx's dictation button, applied once at the shell level since every one of Tingxie's `speakText()` call sites (vocab/sentence/apply/practice "🔊 朗读 Listen" buttons) benefits from it. The shell-level fix only covers *navigation*, not an in-place flip — `Apply.tsx` additionally calls `stopSpeaking()` itself (a `useEffect` on `state.applyFlipped`) so a reading started from the front's Listen button doesn't keep playing after the student flips to the answer; `Practice.tsx`'s sentence phase doesn't need the same guard since its front-side Listen button (see below) and back-side one both read the same text.
- **Data loading**: this was originally the app's only runtime `fetch()` (JSON in `public/tingxie-lessons/`) and is now the pattern every content type follows (questions, Tingxie, Read a Story all fetch from `public/content/p5/` — see the Content files section above) — lesson content is fetched on demand from YAML files rather than bundled as TS imports, specifically so new lessons can be dropped in without a rebuild (`src/data/tingxie.ts`'s `fetchTingxieLessonIndex()`/`fetchTingxieLesson()`, each with a small module-level `Map` cache).
- **Four activities per lesson**, switched via tabs in `Tingxie.tsx`'s top bar once a lesson (or custom review) is active:
  - **Learn** (`Learn.tsx`, `subTab: "vocab" | "sentence"`): 学词语 is a 3D flip-card carousel (`TingxieFlipCard.tsx` — a shared `perspective`/`backface-visibility`/`rotateY` shell reused by Apply/Practice too) over `lesson.vocab`; 学默写 is a sentence-reordering game — word chips (`lib/tingxieSentenceWords()` strips punctuation tokens out of `sentence.segments`) are placed into a tray, and placing them in ascending index order (vs. the shuffled `chipOrder`) is what "correct" means, so the reducer never has to store or re-derive the actual word sequence. Tapping a chip already in the tray (not just the bag below it) removes just that one chip back out (`SENTENCE_UNPICK`, `tingxieState.tsx`) instead of requiring a full reset — also clears a stale "incorrect" result so the tray goes back to editable.
  - **Apply** (`Apply.tsx`, 词语应用): one flip-card per vocab word that has a `sentenceBank` (`TingxieActiveContent.applyVocab`, see `data/tingxie.ts` above) — front shows a blanked example sentence (`tingxieBlankWord()`, literal substring replace) + English gloss, back reveals the word.
  - **Play** (`Play.tsx`, 词云游戏): a 60-second timed round, sitting between Apply and Test in the tab bar. One blanked sentence at a time (built the same way as Apply's queue — `buildTingxieApplyQueue(state.activeContent.applyVocab)`) is shown while word-cloud buttons keep falling down `.tingxie-cloud-sky` (a CSS keyframe fall per cloud, `.tingxie-cloud`/`@keyframes tingxie-cloud-fall` — remounted-via-`key` pattern like the toy minigames' `CatchGame`/`FeatherGame`, not a `requestAnimationFrame` position loop, see those files' comments for why). Tapping the cloud that matches the current blank scores `TINGXIE_PLAY_CONFIG.CORRECT_BP` (+1) and immediately swaps in the next sentence; tapping any other cloud costs `WRONG_BP` (-2) and leaves the same sentence up; a cloud that falls off the bottom unclicked (`onAnimationEnd`) is just removed, no score effect. Distractor clouds are drawn from **every lesson's vocabulary**, not just the one being played (`data/tingxie.ts`'s `fetchAllTingxieVocabWords()`, fetches/caches every lesson via the same `fetchTingxieLesson()` cache `prefetchTingxieLessons()` already warms) — the one activity in Tingxie that isn't scoped to the selected lesson/pooled review. The round's live score is tracked in a plain `scoreRef` (never rendered mid-round, so the total is a genuine reveal at the end, per the feature request) and only turned into a real `awardBP()` call once, when the timer hits 0 — clamped to `Math.max(0, score)` first, so a round that nets negative costs the pet nothing rather than actually debiting BP. Plays a looping `ticker.mp3` for the round's duration (`Sound.startTicker()`/`stopTicker()`, a persistent-`<audio>`-element pattern like `background.mp3`, restarted from 0 every round rather than resumed) — deliberately no "🔊 Listen" button on the blanked sentence here (unlike Apply's front face), since reading the full sentence aloud would speak the missing word.
  - **Play's daily BP cap** (`state/tingxiePlayLimit.ts`, `TINGXIE_PLAY_CONFIG.DAILY_BP_ROUND_LIMIT` = 3): an anti-farming limit specific to Play, since it's the one Tingxie activity a student can replay in a tight loop for fast repeat BP (every other activity's payout is flat-per-lesson-visit, not tap-driven). A day-scoped local counter (`hanyuPracticeTingxiePlayLimit_v1`, same `dateKey()`-keyed reset pattern as `state/specialQuest.ts` — local-only, not synced, since it's a soft per-device limit rather than meaningful progress) tracks how many rounds have been *finished* today (`recordTingxiePlayRound()`, called from `finishRound()` regardless of that round's own score, so a deliberate 0-point round still uses up a slot rather than leaving the cap trivially bypassable). `tingxiePlayRoundsToday() < DAILY_BP_ROUND_LIMIT` is checked once, when a round starts, and locked into a ref for that whole round (`roundCanEarnBPRef`) — a round already in progress when the 3rd finishes can't flip from earning to non-earning mid-round. Once capped: the round plays completely normally (clouds/taps/live feedback all unaffected) and still counts toward the Dictation Today's Mission (`recordTingxieActivityCompleted()`/`checkAndAwardMissionBonus()` still fire) — only the final `awardBP(clamped)` call is skipped. `Play.tsx` shows a `.mission-hint-box` banner ("今天的 BP 奖励已用完...仍可练习") for the whole capped round, and the same box again on that round's `CompleteScreen` (in place of the usual `+N BP` pop, via `bpAmount={capped ? undefined : finalScore}`) stating the round's score without implying it was credited.
  - **Test** (`Practice.tsx` — file/component/reducer-action names all still say "Practice" internally, e.g. `PRACTICE_START`/`state.practiceQueue`; only the user-facing label was renamed to "测试 Test", see below): two phases in one queue — vocab (auto-speaks the word via `speakText()` when each card appears, not on click) then, once that queue empties, sentences (no auto-speak, but the front face has its own manual "🔊 朗读 Listen" button reading the target sentence, so the student can attempt the dictation before flipping — same text is also readable from the back) — the reducer swaps in the sentence-phase queue internally, so the component only dispatches `PRACTICE_START` once per visit.
  - **Completion screen**: Learn/Apply/Test render `common/CompleteScreen.tsx` in place of their normal content once finished (Apply/Test when their queue empties; Learn's `VocabFlipCard`/`SentenceBuilderGame` when every card/sentence is done), playing `Sound.applause()` (not `Sound.gift()`) in the same `awardedRef`-guarded effect that awards that activity's BP — so "finishing something" always looks and sounds the same everywhere it happens, Tingxie or not (Read a Story reuses the same component too, see above). Learn's two sub-activities used to show a small `.tingxie-complete-banner` *below* the still-interactive carousel instead of replacing it; that's gone now — completing either one fully replaces the view, matching Apply/Test. Because both are keyed off a flip/answer-check action rather than a queue naturally emptying, each gates the swap on the flip/result state resetting first (`allFlipped && !state.vocabFlipped` for vocab; `allSolved && state.sentenceResult === null` for sentences) — otherwise "all done" would go true the instant that action fires, one render before Next/Prev would normally clear it, yanking the last card's answer away before the student can read it. Play also renders this same `CompleteScreen`, but on its timer reaching 0 (`finishedRef`-guarded, same one-shot idea) instead of a queue emptying — see the Play bullet above.
  - Apply/Test share a **front-shrink/back-requeue queue mechanic**: a correct self-grade drops the current item off the front; a miss moves it to the back so it resurfaces later the same pass — not persisted between visits. A miss (only) also calls `state/todaySummary.ts`'s `recordTingxieWrong()` — see that bullet in the History/achievements/stats section for what this feeds (the Home "今日学习总结 Today's Session Summary" PDF) and why only misses are recorded, not every item practiced. Play doesn't participate in this store (a wrong tap there isn't tied to one fixed "the answer was X" item the way Apply/Test's self-graded misses are).
- **Tab naming**: the 4-tab bar (`Tingxie.tsx`) reads "📖 学习 Learn" / "✏️ 词语应用 Apply" / "☁️ 词云游戏 Play" / "🔊 听写测试 Test" — the last tab used to say "练习 Practice", renamed since "practice" read as ambiguous with the mode's own overall name ("听写练习 Dictation Practice", still used as the page title/`LessonSelect.tsx`'s `<h1>` and unrelated to this tab rename). Every user-facing string tied specifically to that tab (its completion title, empty-state text, loading text, and `TingxiePicker.tsx`'s "Start Test" button) was updated to match; nothing internal (file name, component name, action types, CSS classes) was touched.
- **Custom review** (`TingxiePicker.tsx`, 自由复习): multi-select checkboxes over the lesson index; on start, fetches every selected lesson and pools them (`pooledTingxieReview()` — samples up to `TINGXIE_REVIEW_VOCAB_COUNT`/`TINGXIE_REVIEW_SENTENCE_COUNT` items for `vocab`/`sentences`, but returns the full merged vocab list uncapped as `applyVocab` for Apply's queue — see `data/tingxie.ts` above) into one synthetic `TingxieActiveContent` fed straight into Apply, Play, or Test (`CUSTOM_REVIEW_SUCCESS`'s `target: "apply" | "play" | "practice"`, matching the picker's "✏️ Start Apply" / "☁️ Start Game" / "🔊 Start Test" buttons). The Learn tab and its BP award are hidden/skipped entirely in this mode — there's no per-lesson "visit" for pooled content.
- **BP**: `TINGXIE_BP_AWARD` in `data/pet.ts` (`VOCAB_LEARN`/`SENTENCE_LEARN`: 10, `APPLY`: 10, `PRACTICE`: 20 — carried over from the source app's point values). Each award fires at most once per mount, guarded by a plain `useRef` in the awarding component (not reducer state) — since Learn/Apply/Test remount fresh every time the student navigates back into them, replaying an activity re-earns BP, matching the source app. Each of these 4 award sites also calls: `state/tingxieProgress.ts`'s `recordTingxieActivityCompleted()`; `state/achievements.ts`'s `logAchievement({ type: "tingxieCompleted", detail: \`${lessonTitle}|${activity}\` })` (surfaces in Home's Recent Achievements feed — which lesson + which activity, see the History/achievements/stats section below); and `state/achievements.ts`'s `checkAndAwardMissionBonus()`, which feeds Home's "听写练习 Dictation Lesson" Today's Mission (see `TodayMission` in the Screens section) and its bonus-BP payout. **Play is the exception**: its BP isn't a flat per-activity constant (`TINGXIE_PLAY_CONFIG` in `data/pet.ts` instead — `CORRECT_BP`/`WRONG_BP` per tap, `DURATION_SEC`, cloud spawn/fall timing), earned live in a `scoreRef` throughout the round and only turned into one real `awardBP()` call (clamped to `Math.max(0, score)`) when the timer ends — but calls the same three completion hooks (`recordTingxieActivityCompleted()`/`logAchievement()`/`checkAndAwardMissionBonus()`) as the other 4, so it's still a 5th interchangeable way to satisfy the Dictation Today's Mission.
- **Sound**: flips/tabs/nav need no explicit call (they're real `<button>`s or `.tingxie-flip-card`, both matched by `App.tsx`'s global click listener, which now also plays a click sound of its own — see Sound below). `Sound.ding()`/`Sound.miss()` for correct/incorrect self-grades and sentence-order checks; `Sound.applause()` for BP-award-on-completion (see the Completion screen bullet above — `Sound.gift()`'s sparkle is no longer used here, only for Bag's routine feed-without-aging-up case).
- **`TingxieFlipCard`'s back face contains real `<button>`s** (TTS, self-grade), so its outer clickable region is a `<div role="button" tabIndex={0}>`, not a `<button>` — nesting a button inside a button is invalid HTML (the same constraint `PetHeroCard` used to have). Its click handler calls `e.stopPropagation()` where needed so a click on an inner button doesn't also toggle the flip.
- **Icon decoration**: `sentence.icon` (a Lucide icon name from the source data) is mapped to an emoji via `tingxieIconEmoji()`'s lookup table in `data/tingxie.ts` (with a `✨` fallback for unmapped names). The source app's `sentence.color` (a Tailwind class) was dropped during the JSON→YAML content migration, since it was never read by any code.

### Pet / BP layer (`src/data/pet.ts` + `src/state/PetContext.tsx`)
`PetProvider` holds `PetState` in `useState`, persisted to `localStorage` under `PET_KEY` (`hanyuPracticePet_v1`) on every change; `usePet()` exposes `{ pet, awardBP, buyItem, giveItem, consumeItem, applyPlayReward, renameOwl, recordQuestionsCompleted }`.

- **Mood is derived, never stored as a live value**: `pet.moodAtCheckpoint` + `pet.lastFedAt` is a fixed pair, and `computeCurrentMood()` decays from that pair fresh on every call (not a decay tick) — this is what makes time-based neglect work without a server, and avoids compounding rounding error from repeatedly decaying an already-decayed number. `growth` is normally monotonic (only earned via feeding/play), with one exception below.
- **Growth decay from prolonged neglect**: unlike mood, `growth` is a real stored value read/compared directly all over the app (age, stage, shop math), so it can't just be derived for display the way mood is — `PetContext.tsx`'s `settleGrowthDecay(pet, now)` is a pure function that decrements it for real. While `computeCurrentMood()` is above 0, `pet.growthDecayCheckpointAt` (a new `PetState` field) is just kept at "now" (no debt accrues). Once mood is genuinely at 0, whole days since that checkpoint are converted to lost growth at `GROWTH_DECAY_PER_DAY_AT_ZERO_MOOD` (`data/pet.ts`, currently 1/day), floored at 0 growth, and the checkpoint advances by exactly those whole days (not to "now") so a partial day carries over instead of being dropped. `PetProvider` calls `settleGrowthDecay()` on mount, on a 15-minute interval (`GROWTH_DECAY_SETTLE_CHECK_MS`) while the app stays open, and on tab refocus (`visibilitychange`) — plus `applyGrowthAndMood()` (the shared helper behind `giveItem()`/`applyPlayReward()`) settles it inline before adding new growth, so a feed right after a long absence starts from the already-decayed value. A pre-existing save with no `growthDecayCheckpointAt` (from before this feature shipped) gets it backfilled to "now" by `loadPetState()`'s merge with `PET_DEFAULT_STATE`, so no old save takes a retroactive penalty for neglect that predates the field.
- **BP** is awarded via `awardBP()`, called from `Quiz.tsx` for MCQ/Fill-in (immediately on grading) and for Long-Answer/Writing-Constrained (from the self-check "✓" handler, guarded by a `bpAwarded` flag on the result item so re-toggling doesn't double-pay).
- **Bag/inventory**: `PetState.inventory` is a `Record<shopItemId, quantity>`. `buyItem()` deducts BP and adds to inventory; it does *not* touch growth/mood.
  - `giveItem()` (food, and the old instant-give path) applies a `ShopItem`'s growth/mood effect *and* decrements inventory in one step — called from `Bag.tsx` once that item's throw animation lands, never directly from the Shop. Toys instead split those two steps across the Play flow (see the Toy minigames section above): `consumeItem(item)` only decrements inventory (called the moment a toy's minigame starts), and `applyPlayReward(item, moodReward)` only applies growth + an explicit mood amount (called once the minigame reports a score) — both share `giveItem()`'s internal `applyGrowthAndMood()` helper so the age/mood math itself isn't duplicated.
  - `applyGrowthAndMood()` is also where the Special Quest wheel's `petFull` quest (see `SpecialQuest` in Screens above) is detected — it computes the resulting mood up front (`Math.min(100, computeCurrentMood(pet) + moodAmount)`, read from the same outer `pet` closure as `newGrowth`/`agedUp`, not `prev` inside the `setPet` updater) and, if that's `>= 100`, checks `state/specialQuest.ts`'s `getTodaySpecialQuest()`/`completeSpecialQuest("petFull")` and awards the bonus BP + logs a `specialQuestComplete` achievement on a genuine (dedup-guarded) completion — this one check covers *both* feeding and toy-play routes to 100% mood, since both funnel through this shared helper.
  - None of `giveItem()`/`consumeItem()`/`applyPlayReward()` log an achievement for feeding, playing, or evolving — pet-interaction events are deliberately not tracked at all (only learning activity is, see `RecentAchievements` above), so a feed or play that crosses into a new `PetStage` is reflected only in the pet's own state, never in the achievement log.
  - `giveItem()`/`applyPlayReward()` both **return `{ agedUp, age }`** (`agedUp` true whenever that call crossed a 100-growth age-year boundary — see the Age note above; always true on a genuine stage evolution too, since every `PetStage.minAgeYears` is itself a specific age) so the caller knows to play `Sound.levelUp()` + show an age-up message instead of the routine `Sound.gift()`.
- **`recordQuestionsCompleted(n)`**: pure increment of `PetState.questionsLifetime`, called once per session from `Result.tsx` — kept arithmetic-only (no achievement logic inside it) so the milestone check can be computed from the pre-call value without reading a stale/batched value back out of context.
- **Naming**: `PetState.name` (default `""`, shown as a placeholder prompt until set), edited via `renameOwl()` (trims, caps at 12 chars).
- Cross-device sync (Supabase) is built — see the Auth / cross-device sync section below. `PetState`'s flat, serializable shape (mentioned there) is exactly what made `PetContext.tsx`'s `savePetState`/`replacePetState` a thin wrapper around the generic sync engine rather than needing any pet-specific serialization code.

### Auth / cross-device sync (`src/state/AuthContext.tsx`, `src/lib/sync.ts`, `src/lib/supabase.ts`, `src/lib/username.ts`)
Username/password login (Supabase Auth under the hood) that syncs a student's progress across devices, layered on top of the existing localStorage stores rather than replacing them — **every store keeps reading/writing localStorage exactly as before**, so the app is fully functional, instant, and byte-for-byte unchanged for a student who never actually creates an account. Sync only ever happens in the background, debounced, and never gates a UI action or blocks initial render once past the login gate below — this is the property that keeps the answer to "does login slow the app down (once you're in)" a hard no.

- **Forced login gate, with a guest escape hatch**: `App.tsx`'s `ScreenRouter` computes `needsAuthGate = status !== "signedIn" && !isGuest` and, when true, renders `<Auth gated />` in place of whatever `state.screen` would normally show (TopNav/`AccountBar` are hidden too, see below) — so a fresh visitor always lands on the login page first, never straight on Home. `isGuest` (from `useAuth()`) is a persisted flag (`hanyuPracticeGuestMode_v1` in `localStorage`, `AuthContext.tsx`'s `continueAsGuest()`) set by `Auth.tsx`'s "以访客身份继续 Continue as Guest" button/`.auth-guest` section, which explains (bilingually) that guest progress stays device-local and won't sync — this is the only way past the gate without actually authenticating. Once set, `isGuest` is never cleared (not even by `signOut()`), so a device that's made this choice once is never re-gated. `ScreenRouter` also now blocks its loading screen on `status !== "loading"` (not just `questionIndexLoaded`), so a signed-in student's session has a chance to resolve before the gate decision is computed, avoiding a flash of the login page. **This means an unconfigured build (`supabase` is `null`, see Setup below) now shows the login page on first visit too** (`status` resolves synchronously to `"signedOut"`), just with sign-in/sign-up producing "登录暂未配置" — the guest button still works with zero config, so the app is still fully usable, just one click removed from instant.
- **Login/Sign out UI placement**: not a `TopNav` item — `TopNav.tsx` has no account affordance at all. Instead `common/AccountBar.tsx` renders as its own small bar directly below `TopNav` (`App.tsx`, `showAccountBar = showTopNav && state.screen !== "auth"`, so it's hidden during Quiz/Result and on the Auth screen itself, same visibility rule as `TopNav`) — "登录 Login" (dispatches `GO_TO_SCREEN "auth"`) when signed out, or `@username` + "退出 Sign out" when signed in; also shows a "访客模式 Guest mode" label when `isGuest` and not signed in, since a guest has no other on-screen indicator of that state.

- **Setup** (see the Running / testing section above): a Supabase project with `supabase/schema.sql` applied, and `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` in `.env.local` (`.env.example` has the names). `src/lib/supabase.ts` exports `supabase: SupabaseClient | null` — `null` whenever either env var is missing, and every caller checks for that instead of throwing, so an unconfigured build just runs local-only. In production (Vercel), these two env vars need to be set in the Vercel project (either via Vercel's Supabase integration, which auto-populates them across Production/Preview/Development, or added by hand in Settings → Environment Variables) — `vite build` inlines `import.meta.env.VITE_*` at build time same as local dev, no code difference between the two. **Also required: turn off "Confirm email"** in that Supabase project (Authentication → Providers → Email) — see the username note below for why.
- **Username, not email** (`src/lib/username.ts`): Supabase Auth has no native username identity, only email/password — and this app deliberately avoids a real-email dependency (email confirmation is friction-only for a kids' practice app with no real password-recovery need). `usernameToEmail()`/`emailToUsername()` deterministically map a typed username to/from a synthetic `<username>@example.com` address (`example.com` is IANA-reserved for documentation/testing, so nothing real is ever contacted even if mail were attempted) and Supabase's normal email/password flow runs underneath, invisibly — `AuthContext.tsx`'s `signUp`/`signIn` take a username string and do this conversion internally; `AuthUser.username` is recovered from `session.user.email` on the way back. **"Confirm email" must be off** for this project specifically because a synthetic address can never receive a confirmation link — left on, every signup gets permanently stuck unconfirmed (and `saveAndSync`/`SyncBootstrap` silently never activate, since `AuthContext`'s `status` never reaches `"signedIn"` without a session). `normalizeUsername()` lowercases before conversion so `Alice`/`alice` don't collide as two different Supabase-level emails; `isValidUsername()` enforces `[a-z0-9_-]{3,20}` client-side before ever calling Supabase.
- **What syncs and what doesn't**: only the four stores with genuine cross-device value sync — `PetContext.tsx`'s `PET_KEY`, `history.ts`'s `HISTORY_KEY`, `achievements.ts`'s `ACHIEVEMENTS_KEY`, `tingxieProgress.ts`'s `TINGXIE_PROGRESS_KEY` (each now `export`ed specifically so `state/SyncBootstrap.tsx` can assemble the list without any store needing to know about sync itself). `todaySummary.ts` and `specialQuest.ts` deliberately stay local-only — both are day-scoped and self-reset at the next calendar day regardless of device, so cross-device sync would add surface area for near-zero benefit.
- **`src/lib/sync.ts`** is the whole engine, and knows nothing about React or which specific stores exist (it operates on whatever key/value it's handed):
  - `saveAndSync<T>(key, value)` — writes `localStorage` immediately (via `lib/storage.ts`'s `saveJSON`, the write-side counterpart to the pre-existing `loadJSON`), and debounces (~2s, coalescing e.g. several BP awards in one quiz) a Supabase `upsert` onto a single `user_state(user_id, key, value, updated_at)` table — `key` is literally the localStorage key string, so no separate key-mapping table exists. No-ops the push half entirely when signed out or `supabase` is `null`; the local write always happens regardless. Every syncing store's write path now calls this instead of a raw `localStorage.setItem`. Stamps the local `hanyuPracticeSyncMeta_v1` map (`{ [key]: updatedAtMs }`) with "now" **only while `currentUserId` is set** (i.e. genuinely signed in, not guest mode) -- a guest session's writes still save locally exactly as before, they just never claim a fresh merge-eligible timestamp. Without this guard, playing as a guest and then logging into an *existing* account could push the guest's recently-timestamped local data over that account's real, older-timestamped remote data during the post-login merge (see `pullAndMergeAll` below) -- a second variant of the cross-account leak `clearSyncMeta()` was added to prevent, this time via guest activity rather than a previous account's leftover session.
  - `applyRemoteToLocal(key, value, remoteUpdatedAtMs)` — the pull-side counterpart, writes local + stamps sync-meta with the *remote's* `updated_at` (not "now"). Kept deliberately separate from `saveAndSync` so a merge-pull can never schedule a redundant push right back to Supabase (a push-after-pull feedback loop).
  - `pullAndMergeAll(userId, syncKeys, { petKey, onPetRow })` — the one-time reconciliation run right after sign-in. Whole-store last-write-wins per key (local sync-meta timestamp vs. Supabase's `updated_at` column — not per-field merging; a kid playing on two devices rarely truly concurrently, same reasoning already used for the Special Quest wheel's dedup guard). A key with no remote row yet just pushes local as-is (an *existing* account's first login on a new device, bringing that device's progress up). **This is deliberately never reached for a brand-new signup** — `Auth.tsx`'s `startFresh()` (see below) resets every synced store to its default the moment `signUp()` succeeds, specifically so a new account never inherits whatever was sitting in the browser's `localStorage` (anonymous local play, or leftover test data) as if it were that new account's progress. This last-write-wins-by-timestamp design is exactly why a genuine sign-out *must* clear local sync-meta too (see `SyncBootstrap.tsx` below) — a stale timestamp left over from a previous account is otherwise indistinguishable from genuinely-newer local data, and could get pushed into a *different* newly-signed-in user's Supabase row.
  - `clearSyncMeta()` — wipes the whole `hanyuPracticeSyncMeta_v1` map. Called by both `Auth.tsx`'s `startFresh()` and `SyncBootstrap.tsx`'s sign-out cleanup (see below), alongside `clearLocalStore()` for each synced key, whenever local storage needs to become a genuinely clean slate.
  - A failed push (offline) is retried on the next successful `scheduleSync` call for that key or on a `window "online"` event.
- **`state/AuthContext.tsx`**: `AuthProvider`/`useAuth()` — `{ status: "loading" | "signedOut" | "signedIn", user, isGuest, signUp, signIn, signOut, continueAsGuest }`. Resolves `status` in the background via `supabase.auth.getSession()` + `onAuthStateChange()` — `App.tsx`'s `ScreenRouter` *does* block rendering on `status === "loading"` (see the login-gate bullet above), unlike the pre-existing `questionIndexLoaded` bootstrap gate which this context has nothing to do with. Calls `lib/sync.ts`'s `setSyncUser(userId | null)` on every status change, the one seam between this Context and the plain `sync.ts` module. `signOut()` itself only ends the Supabase session and does **not** touch `isGuest` — a student who already chose guest-or-login once isn't re-gated just because they signed out of an account — but clearing this account's local data is *not* skipped, it's just not done here (see `SyncBootstrap.tsx` below for why and where).
- **`state/SyncBootstrap.tsx`**: renders `null`, mounted inside both `AuthProvider` and `PetProvider` (see `App.tsx`'s provider tree below) specifically so it can read both `useAuth()` and `usePet()`. Two jobs, both driven by watching `status` transitions (a `prevStatusRef` tracks the previous value across renders):
  - **Sign-in**: the moment `status` reaches `"signedIn"`, fires `pullAndMergeAll()` once per user id (`ranForUserRef` guard). Every synced key except the pet one is fine landing straight in `localStorage` via `applyRemoteToLocal`, since `history.ts`/`achievements.ts`/`tingxieProgress.ts` are never held in long-lived React state — they're read lazily on mount by whichever screen needs them (`loadHistory()`, etc.), so the overwrite is picked up naturally next time. The pet store is the one exception (`PetProvider` loads it once into `useState` at app boot and never remounts), so `pullAndMergeAll`'s `onPetRow` callback routes that one row through `usePet().replacePetState(pet)` instead — a raw state+localStorage replace with no growth/mood business logic, since the remote value already *is* the reconciled result.
  - **Sign-out**: the moment `status` transitions from `"signedIn"` to `"signedOut"` (specifically that transition, not the initial `"loading" -> "signedOut"` resolution on a fresh load with no session — that must *not* wipe a guest's local-only progress) — resets the live pet state to `PET_DEFAULT_STATE` (`replacePetState`), `clearLocalStore()`s the other three synced keys, and `clearSyncMeta()`s the whole timestamp map, then resets `ranForUserRef` so a future sign-in (even the same account logging back in) reliably re-runs the merge-pull above instead of being skipped as "already ran for this user id". **This is required, not optional**: without it, the next login on this device/tab — same account or a different one — silently inherits the signed-out account's leftover local data (pet, history, achievements, Tingxie progress all read straight from `localStorage`/live state, with no per-user isolation), and worse, `pullAndMergeAll`'s last-write-wins merge can push that leftover data into the *newly-signed-in* user's own Supabase row, overwriting their real progress. This was a real bug: two students sharing a device/tab, B signing in immediately after A signed out, ending up with A's pet/history both on-screen and in B's own Supabase `user_state` rows.
- **Provider order** (`App.tsx`): `AuthProvider` wraps `AppStateProvider` wraps `PetProvider` wraps `SyncBootstrap` + `ScreenRouter`. `AuthProvider` has to sit above `PetProvider` so `SyncBootstrap` (mounted below both) can reach `usePet()`; it doesn't need anything from `AppStateContext`, so its position relative to that provider doesn't matter. `PetProvider`'s `loadPetState()` still runs synchronously off `localStorage` in a `useState` initializer exactly as before — merge is always a background reconciliation after first paint, never a render-blocking one.
- **`components/Auth/Auth.tsx`**: the `"auth"` `Screen` (already a reserved union member before this feature existed) — a username/password form toggled between sign-in/sign-up, styled with the `.auth-*` classes in `styles.css`, plus the `.auth-guest` section (see the login-gate bullet above). Takes an optional `gated` prop (`App.tsx` passes `<Auth gated />` when forcing it in place of `state.screen`) that hides the "← 返回 Back" link — there's nowhere to go back to yet on a forced first visit — while a normal (non-forced) visit reached via `AccountBar`'s Login button or `GO_TO_SCREEN "auth"` still shows Back, dispatching `RESET_TO_HOME`. Login (or guest mode) is always reachable, never a genuine dead end. On a successful sign-up specifically (not sign-in), `startFresh()` resets every synced store to its default right there in the success path — `usePet().replacePetState({ ...PET_DEFAULT_STATE, lastFedAt: Date.now() })` for the pet (live React state, same route `SyncBootstrap` uses for a remote pull) and `lib/sync.ts`'s `clearLocalStore()` for the other three (plain `localStorage.removeItem`, safe since every store already treats "key absent" as empty/default) — see the `pullAndMergeAll` note above for why this has to happen before that merge ever runs.

### Owl art (`OwlArt.tsx` + `pet.ts`)
One static PNG per stage × mood bucket lives in `public/owl/` (`owl-<stage>-<mood>.png`, e.g. `owl-baby-happy.png` — 6 stages × 4 moods = 24 combos, `owlSpritePath()`). A combo can instead have a hand-animated **MP4** (H.264 + AAC, sound muxed into the video's own audio track — not a separate audio file, `owlAnimatedSpritePath()`) — currently all 8 `egg-*`/`baby-*` combos, with more of the 24 to follow as they're authored. **There's no hardcoded "which combos are animated" list any more** (there used to be, an `ANIMATED_OWL_VARIANTS` allowlist in `pet.ts` — removed): `OwlArt.tsx` always renders the `<video>` first and only falls back to the `<img>`/PNG if the video's `onError` fires (404, decode failure, ...), tracked in a `videoFailed` `useState` that resets whenever `stageKey`/`mood` changes (so a fresh variant always gets its own attempt at the video, never stuck on a previous variant's fallback) — drop a new `owl-<stage>-<mood>.mp4` into `public/owl/` and it's picked up automatically, no code change needed. A combo whose PNG was deleted after its video replaced it (e.g. `egg-sad`/`egg-neutral`) works fine too, since the `<img>` fallback is only ever reached after a genuine video load failure. The `<video>` has no `loop` (plays once, holds the last frame) and is only unmuted when `OwlArt`'s `playSound` prop is set — on the Home hero card, the Owl screen, and the Bag/"Feed" screen, i.e. everywhere the pet is a primary focus of the screen. `OwlArt` forwards a ref to its root element so `Bag.tsx`'s throw animation can target the owl's on-screen position.

### Sound (`src/lib/sound.ts`)
Only `gift()` (rising triangle-wave glissando, giving an item to the owl in the Bag when it *doesn't* cross an age-year boundary, and reused for Tingxie's BP-award-on-completion) is still a pure synthesized Web Audio waveform — every other effect plays a real MP3 file:
- `click()` — any button press, wired up globally in `App.tsx` via a document-level click listener on `button, .option-label, .tingxie-flip-card`.
- `ding()`/`miss()` — a correct/wrong answer (Quiz MCQ/Fill-in/self-check, Tingxie self-grade/sentence-order); `miss()` stays silent on a skipped/unanswered Quiz question, only a genuine wrong pick plays it.
- `applause()`/`encourage()` — a quiz or Tingxie session scoring ≥90% / <90%.
- `purchase()` — a Shop buy.
- `levelUp()` — a feed crosses a 100-growth age-year boundary, `giveItem()`'s returned `agedUp` (includes but isn't limited to stage evolutions, see the Age note above and `PetContext.tsx`'s `giveItem()`).
- `enterShop()` — opening the Shop screen, from both entry points (`Owl.tsx`'s Shop button and Bag.tsx's empty-bag "Visit Shop" button).
- `bagOpen()` — opening the Bag/Feed screen from `Owl.tsx`'s Feed button.
- `wheelSpin()` — spinning the Home dashboard's Special Quest wheel, `SpecialQuest.tsx`'s `handleSpin()`.

These specific-action sounds are layered *alongside* the generic `click()` sound the global listener already fires for the same button press (see `Shop.tsx`'s `handleBuy()` for the original precedent — `buyItem()` + `Sound.purchase()` right next to the click listener's own `Sound.click()`), not a replacement for it.

**Background music** (`background.mp3`) is structurally different from every other sound above: it's a single `HTMLAudioElement` held in a module-level variable (`bgMusic` in `sound.ts`), not a fresh fire-and-forget element per call like `playFile()` — this survives screen navigation (React unmounting/remounting components never touches a module-level reference) and keeps it from ever restarting from the beginning. `Sound.startBackgroundMusic()` is idempotent (creates the element once, sets `loop = true`, and only calls `.play()` if it's currently paused) and is called from `App.tsx`'s existing global click listener on *every* click, not just button clicks — the standard workaround for browsers only allowing unmuted audio to autoplay after a genuine user gesture: the loop can't start on mount, so it starts on the app's first click, and every click after that is a cheap no-op once it's actually playing (or a retry if that first gesture somehow didn't count). `App.tsx` also has a separate `document.visibilitychange` listener (independent of the click listener) that calls `Sound.pauseBackgroundMusic()` when the tab is hidden and `Sound.startBackgroundMusic()` when it becomes visible again — resuming an `<audio>` element that already played once doesn't need a fresh user gesture, so this doesn't hit the autoplay restriction.

**MP3 files live in `public/sounds/`** (`button.mp3`, `correct.mp3`, `wrong-answer.mp3`, `good-result.mp3`, `need-improvement.mp3`, `purchase.mp3`, `level-up.mp3`, `enter-shop.mp3`, `bag-open.mp3`, `wheelspin.mp3`, `ticker.mp3` — the exact filenames `sound.ts`'s `SOUND_FILES` map expects). Drop a replacement in with the same filename and it's picked up automatically, no code change needed. `ticker.mp3` (Tingxie Play's looping countdown track, see the Tingxie section) is the one entry in this list with no file actually dropped in yet as of this writing — same "missing/404 fails silently" behavior as any other sound here, so Play works fine (silently) until it's added.
- Playback goes through `playFile()` (not the Web Audio API graph used by `gift()`), which pulls an `HTMLAudioElement` from a small per-sound pool (`audioPools`, capped at `MAX_POOL_PER_SOUND` = 4) instead of allocating a `new Audio()` on every call — `getPooledAudio()` reuses whichever pooled element for that sound isn't currently mid-playback, only grows the pool up to the cap for genuine overlap (e.g. several correct dings in one quiz-group submit, staggered via `ding()`'s `delay` param), and once the cap is hit, restarts the oldest pooled instance rather than allocating further.
- **This replaced an earlier "fresh `new Audio()` per call" version** — since `App.tsx`'s global click listener plays `Sound.click()` on essentially every tap app-wide, that version allocated a new element on every single button press; on mobile Safari/Chrome this built up enough memory/audio-session pressure over a long play session to visibly lag the whole app (every screen, not just one, since it was driven by cumulative tap count, not any one screen's state), recoverable only by a full page reload. If a sound-related regression like that shows up again, the pool is the first thing to check.
- Every URL has a `?v=<timestamp computed once at module load>` cache-buster appended — without it, a browser that already cached a stale response for a filename (the pre-launch 404, or a since-replaced MP3) keeps serving that stale response indefinitely since the URL never otherwise changes; this was a real bug (a replaced `purchase.mp3` kept playing the old file) before the cache-buster was added.
- A missing/404 file fails silently (caught, never blocks interaction) — the app runs fine before the files are actually dropped in, just silently.

### History, achievements, and stats (`src/state/history.ts`, `src/state/achievements.ts`, `src/state/tingxieProgress.ts`, `src/state/todaySummary.ts`, `src/state/specialQuest.ts`, `src/lib/stats.ts`)
Every localStorage-backed store below (plus `PetContext.tsx`'s `loadPetState()`) reads through two tiny shared helpers instead of hand-rolling `JSON.parse(localStorage.getItem(key) || "null")` + try/catch at each call site: `lib/storage.ts`'s `loadJSON<T>(key, fallback)` (returns `fallback` if the key is missing, the value isn't valid JSON, or localStorage itself throws) and `lib/id.ts`'s `makeId()` (the `${Date.now()}-${Math.random()...}` id scheme every store here uses for its rows). Store-specific logic — `history.ts`'s id-backfill, `todaySummary.ts`'s day-rollover check — stays at the call site, wrapping `loadJSON`'s result; only the raw parse-with-fallback is shared.
- `history.ts` persists the last 50 session summaries to `localStorage` under `HISTORY_KEY` (`hanyuPracticeHistory_v2`; bump this key if the stored shape changes, to avoid crashing on old data). Each `HistoryEntry` has an `id` (assigned on save; `loadHistory()` lazily backfills `id` onto any pre-existing entries that predate the delete feature) so `Home.tsx` can delete individual rows (`deleteHistoryEntry(id)`) via `RecentAchievements`'s per-row "✕" — there's no bulk-clear any more, see the `RecentAchievements` bullet below. Lifetime, but summary-only — no question-level detail (that's `todaySummary.ts`'s job, see below).
- `todaySummary.ts` persists `localStorage` under `TODAY_SUMMARY_KEY` (`hanyuPracticeTodaySummary_v1`) — the full-detail counterpart to `history.ts`'s lifetime summary, but bounded to **today only**: `loadStore()` discards (and re-persists empty) anything whose stored `dateKey` isn't today's, so this never grows into a second unbounded copy of practice history. Two independent lists:
  - `practiceSessions` (`recordTodayPracticeSession()`, called from `Result.tsx` for every finished quiz session regardless of `mode` — full `QuestionGroup[]`/`GroupResult[]` detail, capped at 20/day).
  - `tingxieWrong` (`recordTingxieWrong()`, called from Tingxie's `Apply.tsx`/`Practice.tsx` `missed()` handlers **only** — i.e. only items the student explicitly self-graded "✗ 答错了/记错了", not every item practiced; deduped by `kind`+`answer` so the front-shrink/back-requeue queue mechanic re-missing the same word doesn't create repeat rows, capped at 100/day).

  Feeds `lib/exportPdf.ts`'s `exportTodaySummaryToPdf()` (see the Home bullet above). Deliberately not wired to `history.ts`'s delete — deleting a `RecentAchievements` row does not remove that session from today's PDF; this store resets naturally at the next calendar day regardless, so the inconsistency window is at most one day.
- `achievements.ts` persists up to the 30 most recent `Achievement`s to `localStorage` under `ACHIEVEMENTS_KEY` (`hanyuPracticeAchievements_v1`), written via `logAchievement()`. Only learning-related types exist (`"missionComplete" | "questionsMilestone" | "storyCompleted" | "specialQuestComplete" | "tingxieCompleted"` — pet feeding/evolving is intentionally never logged, see the `giveItem()` note above).
  - `"tingxieCompleted"` is logged by each of Tingxie's 5 award sites (`Learn.tsx`'s `VocabFlipCard`/`SentenceBuilderGame`, `Apply.tsx`, `Play.tsx`, `Practice.tsx`) right alongside their existing `recordTingxieActivityCompleted()` call, `detail` encoded as `` `${lessonTitle}|${activity}` `` where `activity` is one of `TingxieCompletedActivity` (`"learnVocab" | "learnSentence" | "apply" | "play" | "test"`, `data/types.ts`) — `RecentAchievements.tsx`'s `describe()` splits this back apart to render e.g. "完成听写练习：第一课 (Lesson 1)（词语应用）".
  - **Dedup rules differ by type**: `"missionComplete"` recurs at most once per calendar day (`dateKey`-scoped); `"questionsMilestone"` can only genuinely be earned once ever (`questionsLifetime` is monotonic), so it's deduped by milestone number forever, not just for the day; `"storyCompleted"`/`"specialQuestComplete"`/`"tingxieCompleted"` are never deduped by `logAchievement()` itself (fall through to `isDuplicate === false`) — `"specialQuestComplete"` doesn't need to be, since every call site only logs it once per day anyway, gated by `state/specialQuest.ts`'s own `completeSpecialQuest()` dedup guard; `"tingxieCompleted"` genuinely shouldn't be deduped, since replaying an activity re-earns BP (see the Tingxie section's BP bullet) and the achievement feed should reflect that.
  - Also exports `hasLoggedToday(type)` (checked *before* `logAchievement()` by callers that need to know whether the entry they're about to write is genuinely new, not a dedup no-op — `logAchievement()` itself is fire-and-forget void) and `checkAndAwardMissionBonus(hist, awardBP)`, the single entry point for the "all 3 Today's Missions done" check + `MISSION_COMPLETE_BONUS_BP` payout, called from both `Result.tsx` and Tingxie's four completion sites.
  - There's no bulk-clear for either this store or `history.ts` — both had one (`clearAllAchievements()`/`clearAllHistory()`) behind Home's old "Clear All" button, removed along with that button, see the `RecentAchievements` bullet above.
- `tingxieProgress.ts` persists exactly one thing under `TINGXIE_PROGRESS_KEY` (`hanyuPracticeTingxieProgress_v1`): the timestamp of the last completed Tingxie activity (`recordTingxieActivityCompleted()`/`getTingxieLastCompletedAt()`) — the sole exception to Tingxie's "nothing persists" rule (see the Tingxie section), needed so `TodayMission` can see it after Tingxie unmounts. Deliberately has zero imports from `achievements.ts`/`history.ts` even though its callers always pair it with a `checkAndAwardMissionBonus()` call — `stats.ts` already imports this file, and `achievements.ts` imports `stats.ts`, so importing either back would create a 3-file cycle; callers call both functions directly instead.
- `specialQuest.ts` persists the Home dashboard's Special Quest wheel state (see `SpecialQuest` in Screens above) under `SPECIAL_QUEST_KEY` (`hanyuPracticeSpecialQuest_v1`) — same day-scoped-reset pattern as `todaySummary.ts`: a stored entry whose `dateKey` isn't today is treated as "not spun yet," so the wheel is spinnable again each new day with no explicit reset step elsewhere. `getTodaySpecialQuest()` reads `{ questId, status: "pending" | "completed" }` or `null`; `spinSpecialQuest()` picks a random `SPECIAL_QUEST_TYPES` id and persists it as pending (callers are expected to only call this when `getTodaySpecialQuest()` is `null` — the UI enforces "one spin a day" by never offering a re-spin, not this function refusing to run); `completeSpecialQuest(questId)` is the shared dedup guard every completion hook (`PetContext.tsx`/`PlayGame.tsx`/`Result.tsx`) calls before awarding the bonus BP — returns `true` only the first time, for a `questId` that's genuinely still `"pending"`.
- `stats.ts` is the shared home for date-bucketing/derived-stat logic used across the dashboard: `dateKey()` (local-calendar-day key, DST-safe — not raw ms division), `getTodayStats()` (used by `PetHeroCard`'s subgreeting), `formatRelativeTime()`, plus the Today's Mission helpers `READING_MISSION_CATEGORIES`, `isLessonMissionComplete()`, `getReadingMissionCount()`, `isTingxieMissionComplete()` (reads `tingxieProgress.ts`), `areAllMissionsComplete()` (all 3).

### Styling (`src/styles/styles.css`)
Single global stylesheet, currently a **claymorphism** design system (candy pastel palette, puffy double-shadow cards, pill-shaped bars/badges/buttons, squish hover/press interactions) — this replaced an earlier "scholar's-study" terracotta-and-serif look, itself previewed on just the Home dashboard before being promoted app-wide once approved. Light mode only — there used to be a `@media (prefers-color-scheme: dark)` override block on the CSS custom properties, but dark mode was deliberately removed; don't re-add a dark-mode media query without being asked. No CSS modules/CSS-in-JS — components just reference global class names, and no external fonts/CDNs (the app must keep working fully offline).

Because so many shared classes (`.dash-card`, `.mode-row`, buttons, badges, bars, and each screen's own card classes) already consumed these tokens rather than hardcoding colors, retheming the whole app was mostly a token swap plus per-class border-radius/border tweaks, not a rewrite — the same mechanism the old dark-mode override used to use.
- **`.screen`** (the common wrapper class every top-level screen renders, e.g. `<div className="screen owl-screen">`) carries the shared pastel gradient panel background + big border-radius + padding that every screen sits on. **`.home`** overrides that panel back to `background: none; border-radius: 0` (source order lets `.home`'s rule win over `.screen`'s) — Home deliberately has no single outer "everything card"; each dashboard section (`PetHeroCard`, `TodayMission`, Continue Learning, `RecentAchievements`) is its own `.dash-card` floating directly on the page background instead, not nested inside a bigger enclosing card. `.home` used to also get two blurred, slowly-drifting gradient blobs behind the panel via `::before`/`::after` — removed once the panel itself went away (nothing left to clip/soften them against, see above); `.home`'s ambient-motion flourish today is `ConfettiBackground` instead (see the Home decorative layer bullet below). `.home` also overrides just `padding-top` (down to 6px, from `.screen`'s 28px) — that top padding exists to pad the inside of a boxed panel, and `.home` has no such panel, so on every other screen it's invisible but on Home it was dead space stacking on top of `.top-nav`'s own 20px `margin-bottom`, pushing `PetHeroCard` further from the nav than any other screen's content sits below it. Left/right/bottom padding stay as `.screen`'s.
- **Badges** (`.marks-badge`, `.quiz-bp-badge`, `.pet-status-bp`, `.pet-hero-stage-badge`, `.stat-tile-badge`) used to be a rotated "seal stamp" (carved bevel, `rotate(-3deg)`); they're now unrotated puffy pills (`border-radius: 999px`, `var(--shadow-1)`, `scale(1.06)` on hover) matching the rounder shape language everywhere else.
- **Bars** (`.growth-bar`/`.mood-bar`) are pill-shaped (`border-radius: 999px`) with a `::after` shine sweep (`clay-bar-shine` keyframes, ~3.4s, respects `prefers-reduced-motion`) so they read as gently alive rather than static.
- **Squish interactions**: most interactive cards/buttons (`.mode-row`, `.mission-card`, `.stat-tile`, `.primary-btn`/`.secondary-btn`, `.lesson-btn`, `.shop-item-card`, `.bag-item-card`, `.tingxie-tab`/`.tingxie-subtab`/`.tingxie-picker-row`/`.tingxie-chip`, etc.) lift + scale up slightly on hover and scale *down* on `:active` (rather than the old flat `translateY`), for a tactile "press" feel.
- **Desktop-width layout**: `#root`'s `max-width` used to be a flat 780px at every viewport width, which left large empty gutters on any desktop-width window; it now only clamps to 780px on narrow (phone) viewports and grows up to 1400px from tablet width up (`@media (min-width: 900px)` also adds side padding). Grid-based screens (Home, Practice, Shop, Bag, Tingxie's lesson picker) already used `repeat(auto-fill, minmax(...))` grids, so they reflow into more columns for free. Text-heavy single-column screens opt back into a comfortable reading width: `.screen.quiz`/`.screen.result`/`.story-reading` cap at 780px and center themselves, since a passage of Chinese text stretched to 1400px hurts readability rather than helping it. The Owl and Bag/Feed-Play screens use a shared `.pet-layout`/`.pet-layout-art`/`.pet-layout-info` flex layout (stacked and centered on mobile, art beside stats/actions side-by-side from `@media (min-width: 700px)` up) instead of just letting their content float centered in a wide panel; Bag additionally uses the `.pet-layout-wide`/`.pet-layout-info-wide` modifier since its item grid wants more room than Owl's narrow stat block. `PetHeroCard`'s two hero columns (`.pet-hero-left`/`.pet-hero-right`) are centered as a unit (`.pet-hero-row { justify-content: center }`) rather than pushed to the card's far edges — an earlier `margin-left: auto` push-to-edge trick produced a large empty gap between the two columns on a wide dash-card, which is why it was replaced.
- **Home's decorative layer** (`components/Home/ConfettiBackground.tsx`, `components/common/CursorGlow.tsx`, `components/common/Reveal.tsx` + `lib/useScrollReveal.ts`, plus `TodayMission.tsx`'s mission-card tilt): purely cosmetic, all gated behind `prefers-reduced-motion`/`(hover: none)` where relevant, none of it touches app state.
  - `ConfettiBackground` renders a canvas (`position:absolute; inset:0; z-index:0` behind `.home-content` at `z-index:1`) with density-scaled colorful sprinkles that spring back to their scattered origin but get shoved away from the cursor within a ~110px radius (real per-frame repel physics, not a CSS trick) — `pointer-events: none` so it never blocks clicks; mouse position for the repel is tracked at the `window` level instead. Static (no physics loop) under reduced motion.
  - `CursorGlow` is mounted once app-wide in `App.tsx` (a sibling of `ScreenRouter`, not per-screen) — a single `position: fixed` div that follows the cursor via `--cx`/`--cy` custom properties and blooms from 35px to 160px with a radiating purple pulse (`.cursor-glow-active`, `@keyframes cursor-glow-radiate`) whenever the cursor is over the same interactive-element selector App.tsx's global click-sound listener already uses (`button, .option-label, .tingxie-flip-card`). Deliberately rendered outside any screen's own DOM (a `position:fixed` element's containing block becomes the nearest transformed/perspective ancestor instead of the viewport if nested inside one — Home's 3D-tilted mission cards set exactly that, see below).
  - `Reveal`/`useScrollReveal` replaced Home's old load-only fade-in (`dash-card-in`, which animated once on mount regardless of scroll position, so anything below the fold had already "revealed" before you scrolled to it) with a real `IntersectionObserver`-triggered fade/slide-up, fired once per section and unobserved after. `Home.tsx` wraps each top-level section in `<Reveal delay={ms}>` with a per-section stagger passed as a prop (not nth-child CSS, since some sections are conditionally rendered). Starts already-visible under reduced motion, decided synchronously in `useScrollReveal`'s `useState` initializer so a reduced-motion visitor never renders (and therefore never transitions out of) the hidden frame.
  - `TodayMission`'s 3 mission cards sit in one shared `perspective` (`.mission-grid`) with the left/right cards resting at a static ±10° `rotateY` (`.mission-card:nth-of-type(1|3)`) for a shallow carousel curve, center flat; `tiltMissionCard`/`untiltMissionCard` (mousemove/mouseleave handlers) live-tilt whichever card the cursor is over by writing `--tilt-x`/`--tilt-y`/`--tilt-z` inline (highest specificity, so they override the resting CSS values while hovering and fall back to them on mouseleave), consumed by one `transform: perspective(...) rotateY(var(--tilt-y)) rotateX(var(--tilt-x)) translateZ(var(--tilt-z))` declaration.
